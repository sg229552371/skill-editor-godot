# 项目级 Skill：dev-loop-checkpoint

> 这个目录**要入库**（`.gitignore` 里对 `.workbuddy/skills/` 做了白名单例外）。
> 目的：换设备 / 换 AI 接手时，工作流本身跟着仓库走，不跟着某台机器走。

---

## 这是什么

一份**开发动作的自检与协同流程**，不是技术规范。

技术规范回答「怎么写这个函数」；这份回答「**现在该做什么动作，以及这个动作对不对**」。

三个组成部分：

| 组成 | 位置 | 作用 |
|---|---|---|
| **14 问自检序列** | `SKILL.md` §一 | 每个动作前后过一遍，分 A/B/C/D 四组 |
| **人工决策边界** | `SKILL.md` §三 | L1/L2/L3 三级分类，决定该问还是该查 |
| **人机分工** | `SKILL.md` §五 | 谁擅长什么，三个协作反模式 |

---

## 来历

不是凭空设计的，是**从这个项目真实踩过的坑里提炼的**。

写这份 skill 的触发是制作人一句话：

> 「重点是我在开发过程的所有操作，提问技巧，已经一些反问或提前规划等所有动作。
> 人工参与决策和定方向。简单问题 AI 通过互联网查询，复杂问题无果后提问人工，
> AI + 人工是一体，互相扶持！」

制作人给出的 14 个追问，直接成了 §一 的骨架。其中最后两问
「那它是什么？」「它是干什么？」形成闭环——这是整套流程里最容易被跳过、
也最值钱的两问。

---

## 用法

**不需要通读。** 按场景查：

| 你在做什么 | 读哪一节 |
|---|---|
| 刚接到任务 | §二 表格第 1 行 → 问 ①③④⑥⑬ |
| 卡住了 | §二 表格第 2 行 → 问 ③④⑦⑧ |
| 越改越乱 | §二 表格第 3 行 → 停下，问 ①⑥⑫ |
| 要交付了 | §二 表格第 4 行 → 问 ⑤⑩⑫ |
| 不确定该不该问人 | §三（比 14 问更重要） |
| 怀疑自己在过度工程 | §四 三个信号 |

**一页速查在 §六**，急的话只看那一节。

## 维护

**这份 skill 会随项目成长而变化**。修改时机：

- 又踩了一个「AI 常见的错」→ 加进 §五
- 又发现一条「人工纠错 AI」的典型模式 → 加进 §四（那些教训段落）
- 某个环节反复出问题 → 说明流程本身要改，不是执行力度不够

**不要为了完整而加内容。** §四 已经有一条判据：
> 这条新加的规则，未来有人会为了它改变做法吗？不会 → 别加。

这条判据对本文自身同样适用。
