# 开发动作自检与协同（Dev Loop Checkpoint）

## 这个 skill 解决什么

AI 开发最常见的失败不是「写错代码」，而是**三个更早的失败**：

1. **动作没有目的**——做了一件看起来对的事，但说不清它为什么存在
2. **动作没闭环**——做了，但没确认它真的生效、真的被需要
3. **该问的时候不问，不该问的时候问**——方向由 AI 自己定了，或反过来把查得到的东西推给人类

这套流程不教你写代码。它让你在**每个动作前后**问对问题，并在正确的时刻把决策交还给人。

### 这套流程的来源（不是凭空设计的）

14 问来自制作人对开发过程的逐条追问；边界规则来自**本项目真实踩过的坑**。
下列每一条都能在仓库里找到出处，不是编的：

| 本文条目 | 出自哪次真实事故 | 出处 |
|---|---|---|
| ⑥「回到人类实际说过的话」 | AI 替人拍板目录结构，被连续纠错两次 | 台账 D-52 |
| ③「前置条件没满足就动手 = 制造返工」 | 目录口径没定就先开 B 实验，被叫停 | 会话原话「先不要继续 B」 |
| ⑩「真的生效了，且我能证明」 | 门禁用伤害验证位置，反向注入时没变红（半径蒙对了） | 台账 D-50 |
| ⑩「文档口径改了，引用旧口径的地方改了吗」 | 白名单总账出现 `✅21+●53=74≠65` 内部矛盾 | 台账 D-49 |
| ④「没有客观标准就是该问人的时刻」 | 「水晶」与「辅助宝石」两个名字并存 | 台账 D-14 |
| ⑬「名字会变，而且应该变」 | 「粒子」→「行为名称」、「流派归属」→「辅助类别」 | `00_总纲` §2 |
| §四「治理成本超过产出成本」 | 代码 5658 行 vs 文档 9480 行；近 20 次提交 15 次是 `docs:` | 实测统计 |
| §四「为假设的将来做准备」 | 五条判据被要求先验证再推广，而非直接做成插件 | 实验 B |

> **用这份 skill 的方式**：它不是"建议清单"，是"事故总结"。
> 每一条背后都有一次真实的返工，跳过哪条就会重演哪次。

## 一、14 问自检序列（核心）

**用法**：不是每次都答完 14 问。按场景取片段——见 §二 的「什么时候问哪几问」。
但**任何非平凡动作**（写超过 20 行的代码、改口径、删文件、开新模块）至少要走 ①②③④⑫⑭。

序列分四组，顺序有讲究：**先问目的，再问质量，然后问关系，最后回到起点**。

### A 组｜起点（动手前）

**① 它是干什么的？**
一句话说清这个动作消除什么问题。说不出来 → 不要做。
> 反例：「我要加个缓存」→ 干什么的？→ 「因为听说性能重要」→ 这是理由，不是目的。
> 正例：「加缓存，因为同配置下每帧重复装配 300 次，实测 12ms/帧」

**② 我获得了什么？**
动作完成后，多出来的是什么具体东西？（一个能跑的测试、一个删掉的重复、一个能被查到的结论）
**必须是可指认的**。如果答案是「架构更好了」→ 那是感觉，不是获得。

**③ 它要什么？**
这个动作依赖什么前置条件？（数据已存在、接口已定义、人类已裁定方向）
前置没满足就动手 = 在后面制造返工。

**④ 它对吗？**
有没有一个客观标准能判断对错？
- 有（测试能红、数值能算、文档口径能对照）→ 走验证
- 没有 → **这就是 ⑬ 该问人的时刻**，不要自己发明标准

### B 组｜质量（做完后）

**⑤ 它能更优解吗？**
注意：这问的是「有没有更简单的做法」，**不是「能不能做得更完美」**。
- 更简单 = 该问
- 更完美 = 通常是陷阱，见 §四「过度工程的三个信号」

**⑥ 它是我要的吗？**
回到最初的需求——**不是回到我以为的需求，是回到人类实际说过的话**。
> 这一问经常抓出「我做了个更酷的东西，但没人要」。

**⑧ 我能提供什么？**
我手上有什么是这个任务真正用得上的？（已有的测试、已定的口径、已踩过的坑）
**不要提供"可能有用"的东西**——那是噪音。

**⑨ 我提供的是它需要的吗？**
上一条的自检。最常见的错：给了长篇背景，而对方只要一个决定。

### C 组｜边界与闭环

**⑦ 它边界是什么？**
- 这个动作**不**负责什么？（越界会污染别的模块）
- 什么情况下它会失效？（换引擎/换版本/数据规模变大）
**说不出失效条件 = 你不知道自己在做什么。**

**⑩ 它处理好了吗？**
不是「我做完了」，是「它真的生效了，且我能证明」。
- 代码：测试红了没有？反向注入会红吗？
- 文档：口径改了，引用了旧口径的地方改了吗？
- 结论：这个结论在什么前提下成立，写了吗？

**⑪ 它流程高效吗？**
动作本身有没有绕路？（重复的验证、多余的中间产物、为了流程而流程的步骤）
> 判据：如果这一步去掉，最终产出的质量会下降吗？不会 → 它不该存在。

**⑫ 它得到了最初想到的吗？**
**这一问必须对照 ① 的原文回答，不许重新解释。**
拿 ① 写的「消除什么问题」当尺子，量现在的结果。对不上就是跑偏了——不管中间做得多漂亮。

### D 组｜回到起点

**⑬ 那它是什么？**
做完之后重新命名这个东西。**名字会变，而且应该变。**
> 例：开始以为是「加个工具脚本」，做完发现是「一条门禁」。这个名字变化很重要——
> 工具是可有可无的，门禁是不能不过的。

**⑭ 回到 ①：它是干什么的？**
用 ⑬ 的新名字重答一次。
- 答案和 ① 一致 → 闭环，结束
- 答案变了 → **说明 ① 当初就没想清**，或中途目标漂移了，要回头修正 ①，而不是假装闭环

## 二、什么时候问哪几问

| 场景 | 必问 | 说明 |
|---|---|---|
| 接到新任务 | ①③④⑥⑬ | 先搞清目的、前置、判断标准、是不是人家要的、这到底是个什么任务 |
| 卡住了（报错/没进展） | ③④⑦⑧ | 多半是前置条件缺失，或标准不清，或边界踩到别处 |
| 越改越乱 | ①⑥⑫ | 停下来。回到最初要什么，通常发现目标漂移了 |
| 写完了要交付 | ⑤⑩⑫ | 能不能更简单、真的生效了吗、达到初衷了吗 |
| 发现自己在反复做同一件事 | ⑪ | 流程有冗余，或者根本没找对根因 |
| 想加一个"可能有用"的东西 | ⑥⑦⑧ | 三问连打，基本都能拦下来 |
| 不确定该不该问人 | ④⑦⑬ | 没客观标准 / 说不清边界 / 说不清它是什么 → 该问 |

## 三、人工决策边界（**这一节比 14 问更重要**）

核心原则：**简单问题自己查，复杂问题先查后问，方向必须人来定。**

### 3.1 三级分类

| 级别 | 特征 | 处理方式 | 例子 |
|---|---|---|---|
| **L1 简单** | 有唯一正确答案，能查到 | **自己查，不要问** | Godot API 名称；某函数的参数；某个格式怎么写 |
| **L2 复杂** | 有答案但需要调研、跨源比对 | **先自己查，查不到或结论冲突才问** | 某框架的最佳实践；两种架构的取舍；某个报错的根因 |
| **L3 方向** | **没有客观答案，取决于人的意图** | **必须问，且必须给足选项** | 做不做这个功能；先做 A 还是 B；这个体验是你要的吗 |

### 3.2 L1/L2 违规最伤信任

**把查得到的东西推给人类 = 消耗人类最宝贵的注意力。**

自查门槛（三条都过才允许提问）：
1. 我搜索过吗？（至少 2 个不同角度的 query）
2. 我读过项目内相关文档吗？
3. 我能把「我查了什么、结论是什么、还差什么」说清楚吗？

说不清第 3 条 → 你还没准备好提问，先去查。

### 3.3 L3 提问的正确形态

**错误**：「这个要怎么做？」——把决策成本整包丢回去。

**正确**：给 2–3 个**具体选项 + 每个的实际后果**，让人只需点头或划线。

```
现在的选择：
A. 继续铺内容（能交付更多技能，但治理债继续累积）
B. 先整改测试（解决 D-53 发现的漏洞，但本周无新内容）
C. 先试玩验收（能发现手感问题，但依赖你亲自玩）

我倾向 B，因为 A 会让 R-1 那个漏洞的修复成本每天变高。
```
**注意最后一句**：要给自己的判断和理由，不能只是罗列。人需要的是「你的意见」，不是「选项菜单」。

### 3.4 必须停下来问的六种情况

不要自己发明答案，宁可停下来：

1. **需要项目外的资料**（本仓库文档没写、网上查不到）
2. **两种做法都说得通，且不可逆**（一旦选了，回退成本高）
3. **涉及"什么算做好了"的定义**（验收标准只能人定）
4. **发现文档之间互相矛盾**（口径冲突必须人来裁）
5. **要删除既有东西**（不确定是不是有人依赖）
6. **实现某种效果需要新机制**（不是新代码，是新机制——这属于方向）

## 四、过度工程的三个信号（⑤ 的陷阱）

「能更优解吗」很容易被误解成「能做得更完善吗」。以下三个信号出现时，**答案是"不要做"**：

| 信号 | 表现 | 为什么是陷阱 |
|---|---|---|
| **为假设的将来做准备** | 「以后可能要支持 X，所以先抽象一层」 | 你猜的 X 大概率不是真的 X；抽象层的成本是**现在**付的 |
| **治理成本超过产出成本** | 文档比代码多、检查比被检查的多 | 本项目实测：代码 5658 行 vs 文档 9480 行；近 20 次提交 15 次是 `docs:` |
| **为流程而流程** | 这一步去掉，产出质量不会下降 | 那么它不该存在（⑪） |

> **本项目的真实教训**：48 条决策 / 27 条坑的记录确实救过命，但它到某个点就不再有价值——
> 因为**新决策覆盖的是已经想清楚的事**。判据是：这条新记的决策，未来有人会为了它改变做法吗？
> 不会 → 别记。

## 五、人机互补的分工

**AI + 人工是一体的，但擅长的事不一样。搞错分工，两边都累。**

| 事 | 谁更擅长 | 说明 |
|---|---|---|
| 穷举可能性 | **AI** | 枚举 20 种方案、扫全仓库找引用 |
| 记住已定的事 | **AI** | 但需要你让它写下来，否则会话结束就没了 |
| 判断"这是不是我要的" | **人** | 只有人知道自己的意图 |
| 定义"什么算做好了" | **人** | 验收标准是意图的一部分 |
| 发现"哪里不对但我说不清" | **人** | 直觉是有效的信号源，AI 应该重视 |
| 把直觉翻译成可测的判据 | **AI** | 这是 AI 最有价值的贡献之一 |
| 权衡取舍（时间 vs 完备） | **人** | 涉及价值观和优先级 |
| 执行取舍后的方案 | **AI** | — |

### 5.1 三个协作反模式

**① 人类给感觉，AI 要方案**
人类说「这里怪怪的」→ AI 直接给方案 → 改错了方向。
**正确**：AI 先复述自己的理解（「你是指 A 还是 B？」），确认后再给方案。

**② AI 给菜单，人类做选择**
AI 给 5 个选项让人挑 → 人挑了但不知道后果 → 返工。
**正确**：给 2–3 个选项 + 每个的后果 + **AI 自己的推荐和理由**。

**③ 人类下结论，AI 不质疑**
人类说「这样改」→ AI 照做 → 结果和别的口径冲突。
**正确**：执行前先跑 ④（它对吗）——如果发现和已定口径冲突，**必须先说**，不能默默执行。

## 六、一页速查

**动手前**：它是干什么的？→ 我获得了什么？→ 它要什么？→ 它对吗？
**做完后**：能更简单吗？→ 是我要的吗？→ 边界在哪？→ 真的生效了吗？
**收工时**：高效吗？→ 达到初衷了吗？→ 那它是什么？→ 回到第一问

**该不该问人**：
- 查得到 → 自己查（至少 2 个角度）
- 查了但冲突 / 涉及意图 / 不可逆 / 要删东西 / 要新机制 → 问
- 问的时候：2–3 选项 + 后果 + **你的推荐**

**过度工程警报**：在为假想的将来做准备 / 文档比代码多 / 这一步去掉也没差

**人机分工**：AI 穷举与执行，人定方向与验收。**AI 有意见必须说，人下结论 AI 有异议必须先提。**
