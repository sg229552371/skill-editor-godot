## 二、WorkBuddy 拍板〔推荐默认〕

### D-01 分层：core 与 UI 壳分离

- **决策**：`res://skill_core/` 为纯数据层，**禁止引用任何编辑器 API**；`res://addons/skill_editor/` 为 UI 壳，只调 `skill_core/api/`。
- **理由**：①Godot 编辑器 API 在 `--headless` 下不可测，core 不依赖它才能保证 GUT 100% 覆盖；②用户已确认后续要做游戏内玩家编辑器，同一 core 换 UI 壳即可复用，成本最低。
- **扩展口**：未来第二个宿主（游戏内 UI）直接引用 `skill_core`，无需改动。

### D-02 落盘格式：UTF-8 YAML，自研 `YamlLite` 子集编解码器

- **决策**：`skill_core/schema/yaml_lite.gd` 自研解析器 + 序列化器。
- **依据**：已核实 **Godot 4 无内置 YAML 支持**（仅有 JSON / ConfigFile-INI）。第三方有二：`YAML.gd`（纯 GDScript，MIT，Godot 4.0）与 `godot-yaml` GDExtension（RapidYAML，声明支持 4.3+）。
- **选自研的理由**：①真源 16.1 已明令禁止重复键、自定义执行标签、不能展开为普通值的引用结构、隐式布尔 —— 所需仅是 map/seq/scalar/多行块子集，实现量小；②GDExtension 二进制在 **4.7.1** 上无官方预编译保证，兼容风险不可控；③第三方解析器普遍宽松静默，反而要再加一层拦截；④自研可把「拒收」做成一等公民，直接对应 V-019 / E-0011。
- **退路（扩口，不预先实现）**：若自研超预期，切 `YAML.gd`（纯 GDScript，零编译）；`CfgCodec` 保持后端可切换，JSON 后端作为内部交换/调试快照格式。
- **边界**：YamlLite **只支持**：嵌套 map、seq、标量、引号字符串、`|` / `>` 块、注释、空行。**明确拒绝**：锚点 `&`、别名 `*`、自定义标签 `!!`、多文档 `---`、键顺序语义。拒绝即报错，不静默降级。

### D-20 GDScript 静态复核点：`dict.get(key, {})` 会掩盖「键不存在」（2026-10-18 T-030 血案）

**血案**：`param_resolver.gd:_set_path()` 写成

```gdscript
var child: Variant = current.get(segment, {})   # ← 默认值是新建的游离空字典
if not child is Dictionary:
    child = {}; current[segment] = child        # ← 只有这一支写回父节点
current = child
```

键不存在时 `get` 返回的**临时空字典**本身就是 Dictionary，`not child is Dictionary` 恒为 false →
中间层**从未挂到 root 上** → 所有写入落进游离对象 → `resolved` 恒为 `{}`。
表现是下游 `resolved["params"]` 报 `Invalid access to property or key 'params'`，
**错误表象离根因很远**，极易误判成权限/路径逻辑问题。

- **决策**：涉及「取子节点、不存在则创建」的写法，一律用 `get(key, null)` 作默认值，
  再判 `if not child is Dictionary: child = {}; current[key] = child`。
  用 `{}` 作 get 默认值 = 主动销毁「键是否存在」这一信息，禁止。
- **通用复核点（加入静态复核清单）**：
  ① `.get(...)` 的默认值不得是可变容器（`{}` / `[]`），一律 `null`；
  ② 新建的中间层容器必须**显式写回父节点**再往下走；
  ③ 凡是「写入后读不到」的现象，先怀疑**写入目标是不是游离对象**，而不是去改读取端。
- **诊断手法（有效，保留）**：当 GUT 行号不可靠（报 `at line -1`）时，写一个
  `extends SceneTree` 的最小脚本，分步 `prints` 中间变量（keys / 类型 / JSON 序列化），
  比读 GUT 的截断输出快得多。本例中「sources 正确、resolved 为空」这一矛盾直接锁定了根因。

### D-21 运行期禁止直接解析 Schema 源文档，一律消费抽取后的元数据 JSON（2026-10-18 T-042 血案）

**血案**：`motion.gd:_init()` 写的是
`YamlLite.parse(FileAccess.get_file_as_string("res://S_docs/collab/assets/schema_v0_1.yaml"))`，
结果 yaml 第 4 行一句与运动**毫无关系**的 `$comment: >-` 折叠块让解析失败 → `registered_modes` 为空 →
`configure()` 全失败，报错却是 `Unsupported motion mode: straight`（表象离根因极远，与 D-20 同病）。
一次崩掉 13/14 个用例。

- **决策**：运行期模块**不得**直接读取/解析 Schema 源文档（yaml/md）。需要元数据时，
  由 WorkBuddy 抽取成**小而专用的 JSON** 放 `res://data/`，运行期用内置 `JSON` 解析 + **static 缓存**（进程内一次）。
- **四条理由**（任何一条单独都成立）：
  ① **性能**——每 `new()` 解析 26KB yaml，弹幕场景每秒上百实例，不可接受；
  ② **脆弱**——依赖源文档**全文**可解析，一句注释就能拖垮整个模块；
  ③ **分层**——schema 是校验期/编辑期资产，运行期应消费已提取的元数据；
  ④ **静默风险**——`_init()` 失败只写 `last_error` 不暴露，模块进入"哑火"状态而非报错。
- **已抽取的素材**（同款做法，后续新增照此办理）：
  `res://data/relic_policy.json`（三档权限枚举）、`res://data/motion_meta.json`（运动模式/字段/几何字段）
  源件同步存 `S_docs/collab/assets/` 备查，两份必须一致。
- **失败语义**：素材缺失或解析失败**不得静默降级**——必须写明确 `last_error` 且让入口函数返回失败，
  禁止退化成"看起来正常但能力表为空"。
- **连带**：`_init()` 里**不得**用 RegEx 挖 md/yaml（T-030 曾这么做，同属本条禁令）。

### D-18 GDScript 静态复核点：`:=` 对 Variant 推断失败（2026-10-18 血案）

- **现象**：`var normalized := entry.duplicate(true)`，其中 `entry` 来自 `entries[index]`（无类型 Variant）→ `Parse Error: Cannot infer the type` → **整脚本编译失败** → 依赖它的测试全部报 `Nonexistent function 'new' in base 'GDScript'`，4 个用例全挂。
- **决策**：凡从 `Array`/`Dictionary` 取出的元素、或 `.duplicate()` / `.get()` 的返回值，一律写**显式类型**（`var x: Dictionary = ...`），禁止用 `:=`。
- **成本提示**：这类错误不是单点失败，是**整脚本连带失败**，静态复核必须优先扫这一项。
