# 第 20 章　编辑器自身验收

〔2026-10-18 第1轮〕验收对象是从设计卡输入到 CFG 保存，再到同一运行时复现的整条链。表单能打开、按钮能点、预览能播放都不是完成判定。文档本身的静态校验与未来编辑器实现验收分开报告，本轮不冒称后者已通过。

## 20.1 端到端流程与交付证据

| 步骤 | 操作 | 期望 | 证据 |
|---|---|---|---|
| 填卡 | 从已登记积木创建技能，填写归属、参数、暴露和文字 | 字段单位清楚，锁定项不可改 | 完整设计卡及路径表 |
| 即时校验 | 注入一个非法值再修复 | 报错指向准确字段，修复后旧诊断消失 | V 与 E 编号、实际路径 |
| 整卡校验 | 解析积木、引用、修饰器和表现 | 无阻止保存项，警告可解释 | 校验摘要与依赖指纹 |
| 保存 | 提交并重新加载 | 七键结构一致，版本正确，值无损 | 持久化内容与规范化差异 |
| 预览 | 固定初态、输入和种子运行 | 输出符合对应契约例子 | 事件、结算和调试分栏轨迹 |
| 正式复现 | 从持久化 CFG 在正式入口运行同一夹具 | 逻辑轨迹与预览一致 | 首差异检查结果 |
| 重跑 | 同输入同种子再次运行 | 结果逐次一致 | 两次运行凭据和比较报告 |
| 人审核 | WorkBuddy 核对规则覆盖，用户拍板主观取舍 | 未决项不被伪装为确认 | 审核结论与未通过项 |

验收例子的输入必须非空且能走到目标分支。验证“没有非法事件”时，同时证明至少发生过一次正常 hit 或合法清理；验证“某标签能找到技能”时，先给出预计主键集合，再比较实际结果，不能对空集合执行全部成立判断。失败用例需要证明拒绝原因正确，而不只是按钮没有响应。

每项证据绑定版本和内容指纹。重新保存以后旧测试证据仍可供历史查看，但不能自动贴到新版本上。字段无变化的重复保存不生成假修订；规范化结果变化却沿用同一技能版本时必须阻止覆盖。界面任何绿色通过状态都应能展开到具体用例，不能仅由“未收到异常”推导。

## 20.3 保存、迁移与诊断验收例子

| 编号 | 输入条件与操作 | 预期结果 | 主要检查 |
|---|---|---|---|
| ED-16-01 | 保存完整定义后关闭重开 | 七个顶层键、十二字段卡、七表现段及数组顺序保留 | Schema 往返一致 |
| ED-16-02 | 导入未知顶层键、重复键和结果载荷字段 | 各自拒收，定位原始实际路径 | 不静默丢字段 |
| ED-16-03 | 已知旧版本存在完整迁移链 | 先预览差异，确认后提交，源身份保留 | 迁移策略可执行 |
| ED-16-04 | 未来版本或缺一段迁移链 | 只读，禁止降级覆盖，原文件不变 | V-083、E-0041 |
| ED-16-05 | schema_version 缺失 | 不自动补当前版本，等待明确适配 | 未识别结构保护 |
| ED-16-06 | 保存过程中基线被更新 | 不覆盖，显示打开时与当前版本 | V-081、E-0039 |
| ED-16-07 | 字段错误在第四张积木的覆盖数组内 | 导航到实际叶路径，不停在参数总面板 | 精确定位与来源映射 |
| ED-16-08 | 当前预览已过期，尝试认证新定义 | 可保存合法 CFG，但不沿用旧通过标记 | 保存与认证分离 |
| ED-16-09 | 重复迁移同一内容、重复保存未改内容 | 规范化结果一致，不产生重复转换 | 幂等与版本纪律 |
| ED-16-10 | 默认卡更新影响锁定字段和引用 | 先显示差异，再整体校验，不自动更新旧档 | 默认值稳定性 |

所有 V 规则至少安排一条能触发的反例和一条相邻合法边界。对于通用类型规则，应覆盖零、边界值、缺省、null、字符串数字、非有限数和超范围值；不能只用一个负数证明全部类型检查有效。对于关联规则，必须先构造所有引用存在但语义仍不合法的情形，防止引用错误掩盖越权错误。

## 20.5 可勾选验收清单

### 组织与格式

- [ ] 全部十二个登记角色均完成多技能检索，预计集合与实际集合逐一相等。
- [ ] 共享水晶池、角色限制池、多标签交集和精确 ID 查询均覆盖，结果不重复、不漏页。
- [ ] 增加角色、技能和池只改登记数据，不需要新增固定数量分支。
- [ ] ID 严格符合完整格式，显示名修改不改变身份，变体不充当版本号。
- [ ] `schema_version`、`meta.version` 与文档版本分别展示，不混写。
- [ ] 保存文件只有七个顶层键，每张积木卡十二字段、表现七段与冻结约定一致。
- [ ] 第 5、9 章登记与本稿推荐子字段已由评审合并为同一 CFG Schema；未合并前本项不得勾选。
- [ ] 字段控件、校验、保存、加载使用同一登记来源，不存在各自默认值。

### 校验与诊断

- [ ] V-001 至 V-084 均有触发反例、合法边界和准确定位证据，条件规则按启用能力执行。
- [ ] E-0001 至 E-0042 所有占位均能填入真实值，缺值不显示空白或未定义。
- [ ] 数组错误定位实际下标和叶字段，默认值错误与覆盖错误的来源可区分。
- [ ] 错误、警告、提示对保存和认证的影响一致，不存在导出旁路。
- [ ] 固定运行时策略没有被做成可写开关，未知策略键在导入时被拒收。
- [ ] 所有启用积木具有对应契约探针证据；未通过或过期凭据不能继续认证。
- [ ] 合法预算截断与非法预算配置分开报告，不把所有截断一律阻止保存。
- [ ] 修饰器权限、标签作用域、继承、实时双向声明和受保护字段均有负例覆盖。

### 保存与迁移

- [ ] 正常保存重开后规范化值相同，数组顺序、引用、单位和缺省语义不丢失。
- [ ] 未知字段、重复键、未来版本、缺失迁移链和未识别版本均保护原内容。
- [ ] 迁移差异可查看，重复迁移幂等，不能仅改版本字符串。
- [ ] 保存冲突不覆盖外部内容，失败后保留作者草稿，旧有效定义可继续加载。
- [ ] 当前预览过期时不能沿用旧验证标记，普通保存与通过认证分开。
- [ ] 新默认卡不会自动改变旧定义，目录更新需显式比较和递增技能版本。

### 预览与复现

- [ ] 填卡、保存、重读、沙盒预览、正式入口复现和相同条件重跑完整走通。
- [ ] 预览凭据包含定义、依赖、运行时、夹具、种子和输入，比较前先核对条件。
- [ ] snapshot、实例 params、当前施法者属性和目标当前状态分列，不误称全部实时。
- [ ] 出手、实例、候选接触、hit、份、派生请求分别计数，时间轴不新增技能事件。
- [ ] 全闪避、免疫、无敌、治疗、护盾、控制和击退分支与主书稿验收一致。
- [ ] 同 tick 排序、派生下 tick、死亡跳过、到期不补跳、purge 静默均有证据。
- [ ] 换装原子应用、公共冷却、旧实例不变及 live 受限修改均通过。
- [ ] 关闭表现、换动画、隐藏调试面板后逻辑一致；判定预算截断的差异如实保留。
- [ ] 种子回放逐次一致，差分保留原始顺序，不通过忽略关键字段伪造成功。

### 后续能力与人工审核

- [ ] 模板实例化不携带运行状态，锁定与占位规则符合第 18 章；未实现时明确标未验收。
- [ ] 批量目标集合冻结、失败不半提交、外部版本冲突可停止；未实现时不宣称支持。
- [ ] debug_record 三种 kind 独立展示，不进入正式 UI 或任何逻辑触发。
- [ ] 回放日志缺失、截断或条件不完整时不能认证通过。
- [ ] WorkBuddy 完成规格与证据审核，争议进入未决问题而非擅改已确认决策。
- [ ] 项目性能、联网同步、代码映射和最终数值表未被混入本次完成判定。

## 20.6 本稿交付与实现验收的分界

本次交付只完成章节草案和文档静态检查。清单的空框不是遗漏，而是留给未来实现与评审填写的证据入口。文档校验能够证明章节数、引用小节、编号关联、保存骨架和术语使用的一致性，不能证明编辑器已经运行，也不能证明推荐子字段已被全书 Schema 接纳。

实际实现时遵循规格先行与测试驱动：先选一条上述例子写失败测试，确认失败原因是功能未实现，再实现最小行为并回归。每一轮只推进明确用例，不能先完成整个编辑器再倒推测试期望。人工审核重点是期望是否忠于契约、失败是否真被触发、改动是否越界，而不是单看测试数量。

## 21.1 任务 E 的正确形态：不压测角色清单，压测构造完备性

### 21.1.1 为什么「12 角色技能清单压测」是错的问题

任务 E 原本要求「给 12 个角色的技能清单，逐技能验证能否用现有积木拼出」。用户的判断是对的：**这种压测的形态本身不成立**。

原因有三：

1. **枚举覆盖只能证伪，不能证实。** 就算 12 个角色 60 个技能全部拼得出，也只证明「这 60 个能做」，无法证明「第 61 个没想到的也能做」。而本项目是 Roguelike，技能组合在局内由水晶、遗物、修饰器动态生成，**组合空间本身是开放的**，枚举永远追不上。
2. **它会把设计引向错误方向。** 一旦以「拼出这 60 个技能」为验收目标，最省事的做法就是为拼不出的技能**加专用积木**。积木越加越多、越来越专用，最终退化成「一个技能一块积木」——这正是业界公认的技能系统腐烂路径。
3. **它与项目铁律冲突。** 本项目铁律是数据驱动、逻辑通用、不硬编码。用枚举清单驱动积木设计，等于用内容反推架构。

### 21.1.2 业界证据：高自由度技能系统靠什么支撑

三套公认高自由度的系统，共同点都是**小规则集 + 组合爆炸**，而不是大积木库：

| 系统 | 原语规模 | 组合机制 | 自由度来源 |
|---|---|---|---|
| **Noita 法杖** | 法术 + 修正 + 多重施法 + 触发/定时，四类 | 修正器只作用于**其后**的法术；触发/定时法术命中或到点后才释放载荷，**载荷可嵌套** | 极小规则集产生玩家无法穷尽的组合（官方 Wiki 明确「非乱序杖等价于杖首隐藏一个多重施法块」） |
| **Path of Exile 技能宝石** | 主动宝石 + 辅助宝石 | 辅助宝石链接到主动宝石上改变其行为 | 同一主动宝石配不同辅助链即成不同技能 |
| **UE Gameplay Ability System / AbilityKit** | 成本、冷却、目标定位、效果、实例化策略等原语 | 从原语**组合**出能力；新动作、新条件走**注册表**注册，不改核心 | 「组合优于单体实现」；扩展点显式列出 |

外部事实参考来源（2026-10-18 取得）：
- Noita 法杖机制：<https://noita.wiki.gg/zh/wiki/基礎攻略：法杖機制指南>
- 数据驱动能力系统原则（引用 Epic GAS）：<https://beefed.ai/zh/data-driven-ability-combat-system>
- AbilityKit 扩展点与约束：<https://github.com/MoonNightElf/AbilityKit/blob/master/Docs/design/08-GameplayModules/01-SkillSystemArchitecture.md>
- 技能系统配置复杂度分层：<https://zsummer.github.io/2020/06/16/2020-06-16-lua-oop>

共同结论：**扩展性 = 正交原语 × 组合规则 × 注册机制 × 逃逸口**。缺任何一项，系统都会在内容压力下腐烂。

### 21.1.3 替换方案：覆盖矩阵压测（六维判据）

把「拼得出了哪些技能」换成「积木集合是否构成完备基底」。对**载体 × 结算类型**做二维矩阵，凡是空格，即为真实缺口。

判据如下（六维，全部回答「是」才算完备）：

| # | 维度 | 判据问题 |
|---|---|---|
| P1 | **载体覆盖** | 四类载体 `none` / `self` / `independent` / `attached` 是否都有可用积木？ |
| P2 | **生命周期覆盖** | 创建、移动/持续、命中、派生、终止，五个阶段是否都开放了挂点？ |
| P3 | **结算类型覆盖** | 伤害、治疗、护盾、状态（增益/减益）、召唤、位移、控制、击退、纯表现，九类是否都可达？ |
| P4 | **修饰覆盖** | 数值、时长、范围、数量、目标筛选，五类是否都能被修饰器改写？ |
| P5 | **触发覆盖** | 出手、命中、终止、周期 tick、区域进入/离开，五类是否都能挂触发？ |
| P6 | **逃逸覆盖** | 以上均无法表达时，是否存在受控的脚本/表达式逃逸口？ |

### 21.2.1 实测结论

**整体覆盖率：28 个格子中 14 格已覆盖（50%）。** 这个数字本身不是问题——问题是**空白分布不均**。

五个真实缺口，按严重度排序：

| # | 缺口 | 严重度 | 说明 |
|---|---|---|---|
| **G-01** | **`self` 载体组近乎全空** | **极高** | 四类载体中 `self` 是唯一「位移状态 + 跟随判定体」的载体，承载冲刺、跳跃、有路径命中的位移。当前仅 1 块候选且被 C04-01 阻塞。**这意味着裁决虽然让 `self` 合法了，但没有任何积木能真正用它**——`self` 目前是一个合法但空转的载体。 |
| **G-02** | `independent` 组缺治疗与护盾 | 高 | 移动治疗弹、飞行护盾弹是常见形态，当前无积木可拼 |
| **G-03** | `attached` 组缺控制与击退 | 中 | 附着型陷阱（踩中定身／击退）无法表达 |
| **G-04** | `none` 组缺护盾与状态 | 中 | 瞬发护盾、瞬发上 buff 无法表达 |
| **G-05** | 环境交互与目标约束仅候选 | 中 | 墙面反射缺环境碰撞契约；嘲讽缺索敌覆盖契约 |

**最关键的是 G-01。** 它不是「少一块积木」，而是**整个载体组空转**。第 4 章执笔 CLI 在 C04-01 上主动挂起、拒绝导出位移卡，是正确且专业的行为；但挂起之后必须有人补上这块——否则裁决只完成了一半。

### 21.2.2 G-01 的补齐方案（推荐默认）

建议新增两块 `self` 载体积木，不改动任何运行时契约：

| 建议积木 ID | 名称 | 载体 | 语义 |
|---|---|---|---|
| `self_dash_judge` | 冲刺跟随判定体 | `self` | 施法者进入位移状态，期间生成跟随判定体，对路径上的目标产生 hit；位移结束时判定体随状态终止 |
| `self_leap_impact` | 跳跃落点冲击 | `self` | 位移状态结束（落地）时，在落点产生一次瞬时结算（可挂伤害／控制／击退） |

两者都不新增事件、不新增原因码、不新增载体值，只消费已有的生命周期与结算通道。落点冲击用 `none` 语义的瞬时结算，不新增第五类载体。

**决策状态：已拍板（D-USER-02，2026-10-18）** —— **暂不新增**这两块积木，`self` 载体组在首发中保持为空。

落地要求：第 4 章必须显式标注「`self` 载体当前无可用积木，位移类技能需走 L5 表达式逃逸口」，不得让 `self` 在无声状态下载体空转。L5 逃逸口规格见第 22 章。
