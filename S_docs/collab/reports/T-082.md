## 核心口径（**第 5 轮为准**；早期轮次的表述已被下方修订表取代）

1. **`ok` = 零「有效」诊断**，所有版本同一口径；**`openable` = 内容是否已解析出来并交给调用方**
   （early-failure 与「元数据不可判定」为 `false`；其余可解析的包即使 `ok:false` 也为 `true`）。
   版本不受支持时**只剔除**「版本枚举不匹配」一条（`expected` 以「枚举」开头且 `actual` 等于声明值），
   其余结构/类型诊断照常拦截。
   版本号形态口径（第 5 轮定稿）：**键不存在 / 显式 YAML `null` → `SCHEMA_VERSION_MISSING`**；
   **非字符串（未加引号的 9.9 → float）/带引号 `"null"`/三段式/带符号/前导零 → `SCHEMA_VERSION_INVALID`**。
   可解析的失败包带回 `cfg`/`data`（`data` 为 `duplicate(true)` **副本**，非别名）；
   early-failure 与元数据不可判定时 `cfg`/`data` 为 `null`。
   `skill_list_panel.gd` 改用 `openable` 判定是否打开。
   **边界如实说明**：UI 侧仍要求 `skill_id` / `meta` / `meta.name` 齐全才能进列表，
   因此「身份字段完整、仅结构/类型有错」的破损文件可打开修复；**缺 `skill_id`/`meta` 的文件仍打不开**。
2. **`data` 是 `cfg` 的深拷贝副本**（U-37 第 3 条只增键）：既有消费者
   `addons/skill_editor/ui/skill_list_panel.gd:40` 读的是 `result.get("data")`，缺这个键则 UI 永远报「打开失败」。
3. **版本判定表驱动**：支持版本取自 `data/identity_meta.json` 的 `supported_schema_versions`；
   缺失或为空 → `ok:false` + `metadata` 诊断（不静默全标只读）。代码里没有 `"0.1"` 字面量分支。
4. **读失败与空文件区分**：走 `FileAccess.open` + `get_open_error()`，不再用 `get_file_as_string` 把读错误报成「空文件」。
