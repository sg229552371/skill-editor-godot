## 3. 公开 API 与宿主接线

面板是可 `new()` 的 `VBoxContainer`（`@tool`），不新增 tscn，不接 plugin。

### configure

```gdscript
configure(cfg: Dictionary, entries: Array, exposed: Array,
    metadata: Dictionary = {}, item_policy: Dictionary = {},
    relic_policy: Dictionary = {}, view: Dictionary = {}) -> Dictionary
```

- 返回 `{ok, error, rows?}`；`ok` 只表示面板配置成功，**不是 CFG 合法 / 可保存 / 已授权运行**。
- 前三个参数为注入 CFG、修饰器定义包装列表、暴露字段列表。列表顺序保留。locked 被展示过滤后，`rows` 是可见条数，draft 仍保留隐藏定义。
- 空 metadata / item_policy / relic_policy 参数尝试读取对应现有 `res://data/*.json`；没有默认 UI 授权兜底。view 必须明确注入。
- `entries` 项格式：
  ```gdscript
  {"definition": 六字段修饰器对象, "access": 展示权限key,
   "priority": 可选装配展示信息}
  ```
  `access` / `priority` 是 UI 包装元信息，**不会落入 draft 的修饰器对象**。
- `item_policy.ui_access`：宿主必须注入的 `key -> {visible: bool, editable: bool}` 映射。key 不写死，可以是 author/relic/locked，也可以改名。部署素材缺此列时，返回 `ok:false`，PanelError 点名 `ui_access`。
- view 必填项：
  - `input_path`：draft 的修饰器列表落点；当前宿主应传 `params.modifiers`。
  - `tags_path`：只读标签落点；当前宿主应传 `meta.tags`。
  - `fields`：六键有序描述字典，每项含 `type`。键集合必须与 params_meta 的冻结清单一致；顺序按注入顺序。支持 string/ref、boolean、number/integer、array/permissions、object。
  - `roles`：`scope` / `targets` 语义角色对应哪个字段；类型分别须为 string / array。
  - `tagged_scope`：由宿主提供登记的 tagged 枚举值，不在逻辑里写死该权限/作用域字符串。
  - `field_access`：暴露字段区使用的展示权限 key。
  - `display_access_by_target`：精确路径到展示权限 key，可显式为 `{}`，仅 U-22 过渡展示使用。
  - `new_entry`（可选）：新增模板包装项；有此项则生成新增按钮。不猜测默认修饰器、ID 或运算。
- 测试中的 `_item_policy()` / `_view()` 提供完整接线例子；注入样例仅在测试中，不新增 data。

### 其它公开入口

| API | 行为 |
|---|---|
| `render() -> Dictionary` | 重建 UI；未配置时显式失败并显示错误 |
| `get_draft() -> Dictionary` | CFG 深拷贝；未配置返回空字典，不能当成可保存定义 |
| `get_rows() -> Array` | 可见修饰器的 index/definition/editable 深拷贝，index 是原始 draft 下标 |
| `get_control(index, field) -> Control` | 控件定位；locked / 未登记字段返回 null |
| `get_exposed_control(index, role) -> Control` | 暴露区六组控件定位 |

文本输入按 Enter 提交；数组/对象使用 JSON 文本，布尔使用 CheckBox。JSON 语法错显示错误且不改 draft。目标路径在 targets 数组内，运算引用与操作数在 stack_rule 对象内；不添加单独的 value/operation/priority 落盘键。数值范围、引用登记、继承、live 授权等业务语义必须由后续 core 校验处理。

## 4. 六字段如何保证“不暗加”

1. 修饰器：注入的 fields 数量必须等于 6，并与已部署 Schema 抽取的六键清单逐项核对。每条 definition 的未知键全部收集并点名拒绝，缺键也点名失败。
2. 即使注入者保持数量 6、用 value 替换合法键，也不能绕过冻结清单。
3. 暴露字段：以 T-032 元数据的七个键为允许集合，未知键全部点名；不把 UI 包装信息塞入暴露定义。
4. 暴露区严格六组输入：reference / permissions / bounds / live / inheritable / note；bounds 是单个 `[lower, upper]` JSON 输入，写回两个已登记键，不生成 bounds 字段。
5. 作用域标签与优先级都是 Label，不是输入。新增/删除按钮不充当字段输入。
6. 测试递归遍历全部子节点的 LineEdit / CheckBox / SpinBox / OptionButton / TextEdit，一条修饰器 + 一条暴露登记断言输入数为 **12**，并断言允许集合外数量为 **0**；不是只查“六列存在”。

**口径差异待审核**：任务卡把暴露字段称为六字段，但 T-032 素材与原文均为七键；原文的六字段实际指修饰器。本实现不删减已 PASS 的七键契约，采用范围合并的六组展示。此方案是展示层处理，仍待 WorkBuddy 确认，非已确认的规格修订。
