## 验收硬标准

1. **24 条一条不少，一条不重**：`test_ed17_repro.gd` 里必须是 **24 个** `test_ed17_XX_...` 函数。
   用例另有一条**总账断言**：读 `data/fixtures/ed17.json` 的 `cases`，其 `id` 集合必须**恰好等于**
   `ED-17-01`…`ED-17-24`（用 `range(1,25)` 生成期望值，**不许手写 24 个字面量**）。
2. **每条夹具都必须「真跑」后断言**，不许只判 `ok==true`：
   - 至少断言**预期结果里的那个具体量**（例如 ED-17-01 断言 `hit` 记录数=1、`evaded_all` 存在、派生执行次数=1；
     ED-17-12 断言 X=6 且与实例数/hit 数/份数**分别**取值不等价；ED-17-18 断言末尾只有一条 `hit_end`）。
   - 涉及「有/无」的断言，**先问基线是不是就恒真**（坑 13）：必须构造成「不这么跑就会变」的对照。
3. **做不到的必须显式 BLOCKED，不许空跑、不许桩造成功**：
   `ed17.json` 每个 case 必须有 `status` 字段，取值只能 `"ok"` 或 `"blocked"`：
   - `"ok"`：该条真跑通并通过；
   - `"blocked"`：必须同时给 `blocked_reason`（非空，写清**哪个能力/入口缺失**，贴文件路径+行号）与
     `blocked_probe`（你在测试里**实际探测**该能力的方式，例如调用某入口并断言它返回「未支持」错误）。
   - 测试函数对应 `blocked` 的条目时，断言的是**探测结果**（如「该入口返回显式未支持」），
     **不是**跳过、不是 `assert_true(true)`。
   - 总账断言必须校验：`blocked` 的每一条都有非空 `blocked_reason` 与 `blocked_probe`（防偷懒留空）。
4. **不写回**：每条用例对入参 CFG 前后做 `JSON.stringify` 比对一致。
5. **确定性**：每条用例跑**两次**（同输入同种子），两次 `snapshot_state()` 的关键轨迹一致
   （ED-17-24 本身就是「同输入复现」，但**所有 24 条都要有这一项**，成本很低）。
6. **失败要能定位**：任何一条断言失败，`assert_*` 的失败信息里必须带 `ED-17-XX`（用消息参数），
   不许出现「第 3 个用例挂了」却看不出是哪条。

## 实现约束

- `String(x)` 不是万能转换（`String(Color)`/`String(null)` 运行期炸）→ `str()`（坑 16）。
- 不要 `class_name` 当类型名 → `const X = preload(...)`（坑 15）。
- 素材 / JSON 数字恒 float：需要 int 显式 `int()`（坑 9）；`_` 前缀键是注释，遍历要跳过（坑 11）。
- 测试里**别调 GUT 不存在的方法**（`fail()` 之类）→ 会解析期炸、整脚本不加载、GUT 显示 `Nothing was run`（假绿，坑 12）。
  用 `assert_true(false, "ED-17-XX ...")`。
- 循环遍历 `cases` 时**不要**用 `Dictionary` 当 key 存顺序依赖的东西（顺序不保证）。
