## 三、为什么不用 git worktree
本仓库 5 条泳道写的文件**两两不相交**（见 §4），共享文件（`plugin.gd`、`data/*.json`、`CLAUDE.md`）
**只有审核方改**。worktree 的收益是"防同文件双写"，代价是每个工作树要重新 `--import`
（Godot 类缓存 + `.godot/` 重建，分钟级，且引擎有单实例锁）—— 在当前场景**净亏**。
真正要防的是「CLI 跑 git 回滚误伤他人文件」，这条已在派单里硬禁（`git checkout/clean/stash/revert/restore` 全禁）。

## 五、集成节奏
每波次结束：审核方统一跑门禁 → 全量回归 → 判 PASS → 一次提交（合并成一个 commit，便于回溯）。
**判 PASS 的前提仍是「有原始输出 + 断言未被弱化」**，并发度提高**不降低验收标准**。

## 六、CLI 沙箱的两条硬限制（2026-10-19 实测，写派单时必须遵守）

**① CLI 里跑不了任何 Godot。** 所有 `Godot_v4.7.1` 调用在 CLI 沙箱内都会以
`PROGRAM BLOCKED BY SECURITY POLICY - reg.exe` 失败退出，进程 `status=failed` 但**代码通常已写完**。
→ 派单**不要**再写「改完跑 `--check-only` 自检」，那是执行不了的空指令，只会让会话反复停下等放行。
→ 正确分工：**CLI 只写代码，编译/GUT 全部由审核方串行跑**，有原始报错再回派。
→ 判据：**看文件 mtime 与回执，不看 exit code**。

**② 进程查询也会被拦。** `PowerShell Get-Process` / `tasklist` 走审批，会话会 1 分钟内空转退出。
→ 派单里明确写「不要查进程」，由审核方在派单前确认串行条件。

**③ 破坏式批量改写的代价（T-071 第 2 轮真事故）。** 一次 `continue → pass` 的全局替换，
让 `preview_runner.gd` 6 处循环跳过语义失效，缩进串行崩坏，最终
`test_ed17_repro.gd`（24 用例 947 断言）整片无法加载。**恢复靠 `git checkout` 单文件回滚**。
→ 派单铁律：一次一处精确编辑；禁 sed/正则/replace_all；`continue` 禁止动；整段重写既有文件禁止。
