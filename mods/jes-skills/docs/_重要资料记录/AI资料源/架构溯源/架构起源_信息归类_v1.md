## 一、A 级：可直接使用的硬事实（14 条）

> **入选标准**：① 能用命令或读数当场复算；② 已与本仓库的代码/测试形成对应关系（引用点明确）；③ 不含"AI 说它对"的成分。

### A-1 上游 §3.3 确实是分系伤害（**修正动因之一**）

上游原文（E-10 L110–124）：

```
@export var ... melee_damage / projectile_damage / area_damage / dot_damage | 分系伤害
> 伤害按**分系**（melee/projectile/area/dot）独立累计，行为组件决定技能属于哪个分系；辅助宝石可加对应分系词缀。
```

**现行规格的原话反驳**（`施工规格` §4.1「双维度作用域（对原规格的必要修正）」）：

> 原规格把 `melee / projectile / area / dot` 并列为"分系"。问题是这四者不同类：前三个是**技能形态标签**，`dot` 是**伤害通道**。一个"近战投射物"技能应同时吃 melee 与 projectile 词缀，而"点燃伤害"只吃 dot/ailment 通道的词缀。

**AI 该怎么用**：看到有人提议"合并 Channel 位掩码"或"改回分系"时，把这两段并排摆出来——这不是口味问题，是**上游的缺陷已被识别并修正过**（图谱 N03 / 悬空点 V-08 已关闭）。**不得以"上游就这么写的"为由回退。**

### A-2 上游 §6 装配是「线性跑一遍」（**修正动因之二**）

上游原文（E-10 L222–227）四步：

1. 校验兼容性（tags 匹配 + excluded 排除）
2. 把每个辅助的 modifiers 注入 stats（source_id = 支持宝石 id）
3. behavior_overrides 依序应用（加法先、乘法后）
4. 消耗 = base_cost × Π cost_multiplier × skill_cost_multiplier

**现行规格是六步**（`施工规格` §3.3），且第 2 步是关键差异：

> 2. 先把所有已装配辅助的 `add_tags` 追加到"有效标签集"（**多轮判定，直到收敛**）
> —— 即：靠前的辅助可以"打开"靠后辅助的兼容性

**AI 该怎么用**：上游没有 `add_tags` 字段，所以它**不需要**收敛；现行有 `add_tags`，所以**必须**收敛。谁把收敛去掉，就要连 `add_tags` 一起去掉，否则"靠前的辅助打开靠后的兼容性"这条能力会静默失效（不是报错，是判定错）。

### A-3 上游没有 `add_tags`，只有两个标签字段

E-10 L214–219 实读字段清单：

```gdscript
@export var compatible_tags: PackedStringArray  # ["projectile"] 空数组=全部兼容
@export var excluded_tags: PackedStringArray    # 例如不能辅助召唤
@export var cost_multiplier: float = 1.3
@export var modifiers: Array[ModifierSpec]
@export var behavior_overrides: Dictionary
@export var flags: PackedStringArray
```

**无** `require_tags` / `add_tags` / `conflicts_with` / `stat_modifiers`（后者叫 `modifiers`）。

**AI 该怎么用**：这是"上游 vs 现行"字段级差异的**唯一可比对口径**。任何声称"上游已经支持三元组"的说法都是错的。

### 3.4 一个被上游点明、现行没写的设计点
