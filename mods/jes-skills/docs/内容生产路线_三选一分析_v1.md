# 内容生产路线三选一：A / B / C 分析

**级别**：S6（索引 / 提案层，**不产生规则**）　**版本**：v1　**日期**：2026-10-21
**状态**：**待人类裁定**。本文只把已有证据摊开，**不选路、不预设结论**。
**关联**：规格 §16（暂缓执行）／台账 D-05、D-16、D-17 ／图谱 V-02 ／清单 E-04、E-07、E-08

---

## 0. 一句话：三条路线争的不是"数据存哪"

争的是**「谁是唯一数据契约」**。

| 路线 | 唯一契约 | `.tres` 的身份 |
|---|---|---|
| **A　CFG 驱动** | CFG（七键） | 导入缓存 / 编译产物，可随时重建 |
| **B　自有 `.tres`** | `.tres` | 真源本体，手写或表格生成 |
| **C　适配层双轨** | CFG（源）+ 映射表（桥） | 运行时目标，由 CFG 生成，漂移受检 |

真正的分界线只有一条：**运行时数据模型是不是 CFG 原样**。
是 → A；不是（CFG 编译成 `SkillData`）→ B 或 C。这条界线决定了 261 个用例要不要动，见 §4。

### 1.1 必须说清的两件事

1. **C 没有文档出处。** 它上一轮被推荐的理由是「书自己给了合法出口：`runtime_hints` 明说"即使被忽略也不能改变功能语义"，`player_text` 是作者文案」。这两句**均来自当时读到的书的片段，如今书不可读，无法复核**。按 R5，不能再作为论据；C 目前只是一个**看起来合理的架构形状**，不是有据可依的方案。
2. **B 是既成事实，不是备选项。** 项目已经按 B 走了 18 个 `.tres` + 一整章手册。所以"选 B"的真实含义是**追认现状**，"选 A/C"的真实含义是**迁移**。这一点会显著改变三条路线的成本直觉。

## 2. 结构性障碍：裁 A / C 需要一份读不到的书

```
        ┌─ 想裁 A ─┐
人类 ───┤          ├─→ 需要 CFG 七键的准确定义 ─→ 需要 E-04《技能系统书 v1》
        └─ 想裁 C ─┘                                   ↓
                                                  未入库 ❌
```

> **2026-10-21 投放的两份（E-07 评估书 / E-08 评审一页纸）不解此结**：它们回答的是「选哪个开源方案」（已结案，结论在规格 §1.1），不是「CFG 七键怎么落」。**§16 仍处封冻。**

## 3. 三条路线逐个展开

### 3.1 A：CFG 驱动

**做法**：运行时直接读 CFG（七键）；`.tres` 降为导入缓存，删掉即可重新生成。

**理论收益**
- 作者层与运行层**同源**，不存在"编辑器改了、仓库没跟上"的漂移。
- 书第 14／18／21 章已给校验规则、模板批量事务、覆盖率判据 → 直接**引用**，不必重造（这正是规格 §16 被判"重复发明"的原因）。
- 与姊妹项目编辑器对齐，不必维护转换器。

**对现有项目的实际冲击**（按今天代码实测）

| 面 | 冲击 | 依据 |
|---|---|---|
| 内容 | 18 个 `.tres`（8 主动 + 9 辅助 + 1 触发器）需重写为 CFG | `content/gems/` 实测 |
| 加载层 | `GemRegistry`（含 `_load_dir` / `_ensure` / `reload`）换成 CFG loader | `gem_registry.gd` |
| 数据类 | `SkillData` / `SkillPart` 若被 CFG 原样取代 → **9 个数据类全部重定形** | `systems/skills/data/` |
| 测试 | **取决于"是否保留 `SkillData` 类型"**：保留 → 71 处调用点不动；不保留 → 大面积重写 | 见 §4 |
| 门禁 | `GemRegistry` 的数量断言、`test_content_registry` 的 8/9 计数需同步 | P-23 教训 |
| 新增能力 | 需要 `bricks（十二字段）→ parts` 的展开规则；**该规则书里是否有、长什么样，今天无法确认** | E-04 不可读 |

**最大风险**：把「书里那套作者层模型」直接搬进运行时，会让 `SkillPart` 的"行为 + 数值"紧凑结构被 `brick_id / tagline / author_params / locked_params / relic_params / player_text / status` 这些**纯作者字段**污染。`locked_params` / `relic_params` 明显是编辑器概念，运行时不需要。

> 这一条恰恰是 C 存在的理由，也是 A 的"激进版"与"温和版"的分水岭。

### 3.2 B：自有 `.tres`

**做法**：`.tres` 是唯一真源；CFG 只当设计文档，靠人/工具转换。

**理论收益**
- **零迁移成本**：与 D-05、手册 §6、18 个内容、261 用例完全一致。
- 保留 Godot 原生能力：类型检查、编辑器内预览、`Resource` 导入缓存、`duplicate(true)` 语义（P-17 就是靠它修的）。
- 手册 §6 的六条硬规则已经是可执行施工法，**今天就能继续手写第 9 个主动**。

**代价**
- 与编辑器侧**分叉**：编辑器产 CFG，仓库要 `.tres` → 中间必须有转换器或人工搬运，否则两份定义必然不同步（这是 2026-10-20 的原始判断，**E4 级，需在拿到书后复核**）。
- 批量生产**仍无解**：§16 想要的生成器 / lint / 覆盖率，换成 B 也照样要做，只是输入从 CFG 变成 CSV 或表格。B 不解决"量大了怎么办"。
- 若书的 CFG 是团队约定，B 等于单方面宣布作废——这是**协作决策**，不是技术选型。

### 3.3 C：适配层双轨

**做法**：CFG 为源、`.tres` 为运行时目标；写 loader + 映射表；忽略键（如 `player_text` / `status` / `runtime_hints`）**显式列白名单**，不偷偷丢。

**理论收益**
- 保住现有 261 用例与 18 个内容（因为运行时仍是 `SkillData`）。
- 与编辑器同源，不制造第二份定义。
- 有损映射**写进白名单**，将来能审计"丢了什么"——这比 A 的"整体替换"和 B 的"各自演化"都更容易验证。

**代价**
- **双轨 = 两个真源**，必须靠"生成 + 漂移检查"（规格 §16.2 的 `git diff --exit-code content/`）来锁死，否则两轨必然分叉。
- 映射表本身要成为受门禁保护的文件（1:1 / 有损 / 书有码无 / 码有书无 四类逐字段）。
- **依赖书**：映射表逐字段对照，书不可读就写不出来 → 与 A 同卡在 §2 的循环依赖上。

## 4. 一个改变成本直觉的实测发现

上一轮（2026-10-20）曾判断 A 路线要「243 用例大面积重写」。**今天的代码实测不支持这个结论**：

| 实测项 | 数字 | 含义 |
|---|---|---|
| 测试中 `GemRegistry.xxx()` 取值 | **71 处** | 全部经由唯一入口 |
| 测试中 `SkillData.new()` / `SkillPart.new()` 直接构造 | **3 处** | 极少数 |
| 测试中直接 `load("res://…/content/…tres")` | **0 处** | 内容来源被完全封装 |

**结论**：D-05 定的「唯一入口 `GemRegistry`」真的生效了——**内容从哪里来，对 261 个用例是透明的**。

所以三条路线的代码冲击，可以压缩到**一个类 + 9 个数据类**：

```
GemRegistry（换加载器）  ←  真正要改的地方
      ↓ 必须仍返回 SkillData
9 个数据类               ←  仅当"运行时模型不再是 SkillData"才需要重定形
      ↓
71 个测试调用点           ←  只要类型不变，一行都不用改
```

**于是判据变成一句可操作的话**：

> **运行时拿到的对象，是不是仍然是 `SkillData`？**
> 是 → 无论 A / B / C，测试都不动，成本集中在加载层与转换层。
> 否 → A 的激进版，测试、沙盒、门禁全动，且要吃下 `brick` 的作者字段污染。

这条判据把"选哪条路"从一个抽象的架构争论，变成**一个可以当场回答的技术问题**。它也是本文最重要的一条发现。

## 5. 影响对照表（同一把尺子）

| 维度 | A（激进：CFG 原样进运行时） | A′（温和：CFG 编译成 SkillData） | B | C |
|---|---|---|---|---|
| 现有 18 个内容 | 重写 | 重写（转换脚本） | 不动 | 重写（转换脚本） |
| `GemRegistry` | 重写 | 换加载器 | 不动 | 换加载器 + 映射表 |
| 9 个数据类 | 重定形 | 不动 | 不动 | 不动 |
| 261 用例 | **大面积重写** | 基本不动 | 不动 | 基本不动 |
| 与编辑器同源 | ✅ | ✅ | ❌ 分叉 | ✅ |
| 需要 E-04 原书 | ✅ 必须 | ✅ 必须 | ❌ 不需要 | ✅ 必须 |
| 批量生产方案 | 书 §18 模板 | 书 §18 模板 | 自建 CSV→`.tres` | 书 §18 + 生成 |
| 手写单条内容 | 不可（要写 CFG） | 可 | **可（手册 §6 现成）** | 可 |
| 今天能否开工 | ❌ | ❌ | ✅（仅单条，不批量） | ❌ |

> **A′ 与 C 的区别只在"映射表写在哪"**：A′ 把转换写进代码，C 把转换写成显式映射表 + 白名单。C 更贵，但可审计；A′ 更省，但有损部分会被代码吞掉、看不出来。

## 6. 对"现在"的影响：其实只有一条硬约束

无论最终选哪条，**今天都不该做的事只有一件：批量生产线**（生成器 / lint 9 条 / CSV 设计台）。
理由与路线无关：那套东西的**输入格式**由路线决定，输入没定就建流水线，等于先造模具再决定注什么料。

而**今天允许做的事**也有明确边界：

| 允许 | 依据 |
|---|---|
| 单个技能 / 辅助**手写** `.tres` | 手册 §6（S1）＋ 01 执行版「三类产物」；§16 只封"批量产"，不封"手写一个" |
| 修与路线无关的代码缺陷 | 图谱 V-02「只做线路无关的缺陷修复」；R12 已按此修 `GemLevelScaling` |
| 补契约测试、扩断言 | 不变式，与路线正交 |

**但有一条内部矛盾必须先记下来**：规格 §16 说「手册讲"写什么、怎么写"，**不受路线影响**」。这句在 B 下成立，在 A 下**不成立**——若走 A，手册 §6「手写 `.tres` 的六条硬规则」整体作废，第 12 行「产物只有一种 `.tres`」直接冲突。所以：

> 「手册不受路线影响」这句话本身是**路线 B 的隐含假设**，不能当公理用。裁定路线时，它必须一并被重新审视。

## 8. 如果人类裁定后该做什么（三条路的落地清单）

**若裁 B（追认现状）**
1. 规格 §16 重写为「表格 / CSV → `.tres`」路线，删除对 CFG 七键的全部依赖；
2. 手册 §6 保持不变，明确它是 B 路线下的施工法；
3. 记 D-21：「CFG 七键不进入本仓库运行时，编辑器侧若产出 CFG 须自行转换」；
4. 图谱 V-02 结项。

**若裁 A 或 C**
1. 人类投放 E-04 至 `docs/reference/spec_技能系统书-v1.md` 并登记 E-09；
2. 产出《CFG 七键 ↔ Godot 类 字段映射表》（四类：1:1 / 有损 / 书有码无 / 码有书无）；
3. 由映射表反推：`SkillData` 要补哪些字段、`brick` 展开规则怎么写、忽略键白名单列什么；
4. 才允许动 `GemRegistry` 与内容转换；
5. 记 D-21（路线裁定），规格 §16 按结论重写。
