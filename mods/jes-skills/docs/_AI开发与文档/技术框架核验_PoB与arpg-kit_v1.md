## 一、第一条线：引用库到底在不在项目里（E0，可 grep）

### 1.1 `godot-arpg-kit`：实测零痕迹

```
grep -rin "arpg.kit|arpg_kit|ClarkWain" --include=*.gd --include=*.godot --include=*.cfg .
→ 0 结果（排除 .godot 缓存）
```

| 检查项 | 实测 |
|---|---|
| `addons/` 内容 | `godot_ai`、`gut` —— **无 arpg-kit** |
| `project.godot` autoload | 仅 `_mcp_game_helper`（编辑器插件）；**无 `CombatEventBus` autoload** |
| 目录结构 | `mods/jes-skills/systems/` 自有 48 个 `.gd`；无 `scripts/combat/`、`scripts/stats/` |

> **对照**：kit 官方 `project.godot` 里注册了 `CombatEventBus="*res://scripts/combat/combat_event_bus.gd"`（见 §三 实测）。本项目**没有沿用这个 autoload 路径**，而是自己写了 `systems/skills/combat/combat_event_bus.gd`。

**判定**：`godot-arpg-kit` **不是本项目的依赖**，甚至不是子模块、不是 vendored 副本。它是一个**只被读过一次的参考仓库**。

### 1.2 `PathOfBuilding`：连"读过"都只落在一张表里

```
grep -rin "PathOfBuilding|PoB|CalcOffence|requireSkillTypes" mods/ 
→ 命中全部在 docs/（规格附录 A 的读取清单 + 评估书），代码 0 命中
```

**判定**：PoB 没有被引入（Lua 本来也进不了 GDScript），它的作用是**"标准答案对照表"**——规格 §4.3 的转换规则、§3.3 的三元组、§7.2 的触发限流，都是"按 PoB 校对过"的结论，但**代码是重写的**。

### 1.3 那"落地"到底落的是什么

**结论：抄的是"形态"，不是"代码"。** 三个具体形态：

| kit 的形态 | 本项目的落地 | 证据（E0） |
|---|---|---|
| `RefCounted` 纯函数管线 | 48 个类中 **37 个** `extends RefCounted` | `grep -rl "extends RefCounted" systems/` |
| `StatModifier` 数据形态 | `systems/skills/stat_modifier.gd` + `data/modifier_spec.gd`（两条：规格态 / 运行时态） | 文件存在 |
| 事件总线 autoload | 自有 `combat_event_bus.gd`（**路径与 kit 不同**） | 文件存在 |

### 2.2 架构五层（与规格 §1.1 逐条对照）

### 2.3 规格 §1.1 四层的**实际履行率**

| 规格写的 | 实测 | 履行 |

## 四、第四条线：三条路线"来源很奇怪"——你的直觉是对的

### 4.1 奇怪在哪里：三条路线的**证据级别完全不同**

| 路线 | 来源 | 证据级别 | 能不能今天复核 |
|---|---|---|---|
| **A** CFG 驱动 | 《技能系统书 v1》卷一 3.1「CFG 是编辑器与运行时之间唯一的数据契约」 | **E1**（只有规格 §16 的**转述**，原文不可读） | ❌ |
| **B** 自有 `.tres` | **D-05 已裁定**「内容真源 = `content/gems/**/*.tres`」+ 手册 §6「手写六条硬规则」+ **18 个 `.tres` 已在仓库** | **E0**（代码可直接看） | ✅ |
| **C** 适配层双轨 | **2026-10-20 由 AI 提议，人类从未拍板，无任何文档原文** | **E4**（印象） | ❌ |

**这就是"奇怪"的来源**：三条被并列摆在桌上、看上去平等的路线，其实**一条是已执行的代码事实，一条是不可读文档的转述，一条是我自己的提议**。并列本身制造了"三条都有依据"的错觉。

### 4.2 更严重：C 的论据已经失效

我上一轮推荐 C，理由是「书里 `runtime_hints` 明说"即使被忽略也不能改变功能语义"，`player_text` 是作者文案，这些本来就不该进运行时」。

**这句话来自当时读到的书片段。书现在不可读（E-04 未入库），无法复核。** 按 R5 与图谱的「E4 不得作为依据」，C 现在**只是一个看起来合理的架构形状**。

> 换句话说：**C 是"我猜书里应该这么写"，不是"书里这么写"。** 这个区别必须写在纸上，否则下个 AI 会把 C 当成有出处的方案继续推荐。

### 4.3 还有一个更根本的错位

三条路线被描述成"内容生产路线"，但**它们的真正分歧不在生产，在运行时**：

| 路线 | 运行时拿到什么 | 谁是真源 |
|---|---|---|
| A | CFG 原样 | CFG |
| B | `.tres` 反序列化的 `SkillData` | `.tres` |
| C | CFG 编译出的 `SkillData` | CFG（`.tres` 是产物） |

所以这不是"三条一样好的路"，而是**"要不要让 CFG 进来"**这一个二选一，加一个"以什么方式进来"的折中。**B 是"不进来"，A 是"原样进来"，C 是"编译后进来"。**

### 4.4 判据（实测支撑）

| 实测（本次） | 数字 |
|---|---|
| 测试经 `GemRegistry.xxx()` 取值 | **71 处** |
| 测试直接 `SkillData.new()` | **3 处** |
| 测试直接 `load("res://…content…")` | **0 处** |

因为内容来源被 `GemRegistry` 完全封装，**"运行时是否仍是 `SkillData`"** 就是唯一的分水岭：

- **是**（B / C / A′）→ 261 用例一行不动，成本只在加载层

## 五、代码里发现的一处**字面级偏差**（不是 bug，但必须记）

规格 §4.2 写：

> ① 取基础值 → ② 加平值 → ③ 伤害转换 → ④ 加算百分比 → ⑤ 乘算百分比 → ⑥ 暴击 → ⑦ 目标侧减免
> **必须**：④ 与 ⑤ 之间不得插入任何逻辑。

`damage_pipeline.gd` 的实际写法（L77–85）：

```gdscript
for el in work:
    var v: float = work[el]
    v = v * (1.0 + inc.get(el, 0.0) / 100.0)   # ④
    v = v * more.get(el, 1.0)                  # ⑤  ← 与 ④ 在同一循环内
```

| 判定 | 说明 |
|---|---|
| 数学结果 | ✅ **正确**。`v×(1+Σinc)×Π(1+more)` 与分两趟逐元素等价 |
| 规格字面 | ⚠️ **不完全符**。④⑤ 同循环，若将来有人在两行之间插逻辑，就真的插进了"④⑤之间" |
| 是否该改 | **不该现在改**。属"路线无关的缺陷"但非缺陷；改外观无收益，且会动已全绿的热路径。**记入台账 P-*，作为"若将来要插逻辑必须先拆分"的预警** |

> 这条正好示范了什么该查：**规格说"不得插入"，代码没有插入逻辑，只是把两步写在一起**。是"字面不符、语义合规"。不作大动，但要留痕。

## 七、修正后的准确表述（给后续 AI 的一句话）

> **本项目是 Godot 4.7 原生 + 全自研 GDScript 技能系统**（3228 行 / 261 用例 / 18 份 `.tres` / 零第三方运行时依赖）。
> **PoB 语义**＝算"该长什么样"的对照表（七步顺序、转换归一化、三元组），已落成规格 §4/§3.3，**代码是重写不是移植**。
> **godot-arpg-kit 落地**＝只借了三样形态（`RefCounted` 纯函数、`StatModifier` 结构、事件总线），**未引入任何代码，故不构成依赖**。
> 因此说"用 PoB + kit 做框架"**不准确**；准确说法是"**以 PoB 为校对标准、以 kit 为形态参考的自研框架**"。
