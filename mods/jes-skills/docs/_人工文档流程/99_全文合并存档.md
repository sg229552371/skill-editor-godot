# 内容设计手册 · 技能与辅助宝石（AI 执行版）v1

> **性质**：这是**内容创作的手册**，不是代码规格。字段的权威定义在《施工规格》§3；本文只回答「要做一个技能/辅助，该怎么想、怎么写、怎么自检」。
> **读者**：负责往 `content/gems/` 里灌内容的 AI。
> **前置**：读过《施工规格》§3（数据契约）与 §13（禁止事项）。
> **地位**：S1 级文档（与施工规格同级）。与代码冲突时以代码为准，并立即修正本文。

---

## 0. 三十秒说明

你要产出的东西只有一种：**`content/gems/**/*.tres`**。不是代码，不是脚本，不是新字段。

**三步**：

```
选一个设计模式（§2） → 按 §1 的行为/标签填字段 → 按 §6 写成 .tres → 跑 §8 自检
```

**三条禁令**（违反即返工）：

1. **不得使用任何 Path of Exile 的技能名、图标、数值**（规格 §13.4 第 14 条）。模式可以借，名字与数字必须原创。
2. **不得为某个技能改 `.gd`**（规格 §13.1 第 1 条）。需要新能力时，先确认是不是「已有行为的参数组合」；确实不是，才走「新增行为」流程（§1.5）。
3. **不得发明字段或标签**。标签必须在 `TagRegistry.DEFS` 里，stat 必须在 `StatRegistry.DEFS` 里，行为必须在 `SkillExecutor.BEHAVIORS` 里。不在表里的名字 = 静默不生效。

## 1. 能力边界：先知道能做什么

### 1.1 七个行为（引擎已有的全部空间形态）

| `behavior_id` | 空间形态 | 必填 `behavior_params` | 可选 | 典型用途 |
|---|---|---|---|---|
| `bhv_projectile` | 从施法者飞出的弹体 | `speed` / `radius` / `lifetime` | `count_base` / `spread_deg` / `pierce` / `fork_count` / `chain_count` | 冰矛、箭矢、飞弹 |
| `bhv_melee_swing` | 身前扇形 | `range` / `arc_deg` | — | 挥砍、横扫 |
| `bhv_aoe_burst` | 定点圆形爆炸 | `radius` | `delay` / `hit_count` / `hit_interval` | 新星、砸地、烈焰 |
| `bhv_channel` | 持续引导、按 tick 结算 | `max_channel_time` | `tick_interval` | 光束、持续灼烧 |
| `bhv_summon` | 生成可行动的召唤物 | `max_count` / `lifetime` | `scene_path` | 随从、图腾、哨塔 |
| `bhv_dash` | 位移并沿途结算 | `distance` / `speed` | `path_damage` | 冲刺、突进 |
| `bhv_buff_self` | 给自己加一组修饰符 | `buff_mods` / `duration` | — | 狂暴、护盾、增益 |

**四条使用铁律**：

- `count_base` 是**投射物基础发数的唯一合法键**。写 `projectile_count` 会被 stat 管线覆盖（`_stat_value` 只认 `count_base`），这是台账 P-06 记的坑。
- `pierce` / `fork_count` / `chain_count` 既是 params 的 base，也是可被辅助宝石改的**整数型 stat**；三者走 `StatRegistry.finalize()` 末端统一 floor，**你写整数即可**。
- `area_size` / `duration` 不进 `behavior_params`，它们是**倍率型 stat**，由辅助宝石的 `stat_modifiers` 提供，管线自动乘到 `area_mult` / `duration_mult`。
- `bhv_summon` 的 `max_count` 语义是「同时存在的上限，到顶后顶掉最旧的」，**不是一次召唤 N 只**（D-10）。

### 1.2 十四个标签（`TagRegistry.DEFS`，不得新增未注册的）

| kind | 标签 | 作用 |
|---|---|---|
| `damage_type` | `physical` `fire` `cold` `lightning` `chaos` | 决定吃哪个 `<元素>_damage` 与 `<元素>_resistance`；必须与 `StatRegistry.ELEMENTS` 一一对应 |
| `cast_type` | `attack` `spell` | 决定吃攻击系还是法术系词缀；辅助宝石的 `require_tags` 大量依赖它 |
| `form` | `melee` `projectile` `aoe` `channel` `movement` `summon` `buff` | 决定能挂哪些辅助宝石（兼容性主战场） |

**一个技能 = 1 个 cast_type + 0~2 个 damage_type + 1~2 个 form**。四个及以上标签基本说明设计没收敛。

> 标签是**兼容性开关**，不是装饰。少写一个 `projectile`，所有投射物辅助都挂不上去；多写一个 `melee`，近战专用辅助会误判兼容。

### 1.3 三条伤害通道（`SkillChannel`）

| 值 | 通道 | 含义 | 与标签的关系 |
|---|---|---|---|
| 1 | `HIT` | 直接命中伤害 | 吃 `<元素>_damage`、暴击、`crit_multi` |
| 2 | `DOT` | 持续伤害 | 只吃 DOT 通道词缀，**不吃** hit 加成（G9 断言的就是这条） |
| 4 | `AILMENT` | 异常状态伤害 | 点燃/中毒/流血等，独立通道 |

**默认是 `HIT`（=1），不写即可**。只有做"灼烧/中毒/流血"类技能时才显式写 `damage_channel = 2` 或 `4`。

### 1.4 选型决策表：想做 X，用哪个行为

| 你想要的效果 | 行为 | 关键参数 | 需要补的标签 |
|---|---|---|---|
| 直线飞出、打中一个人 | `bhv_projectile` | `count_base=1`, `spread_deg=0` | `projectile` |
| 一次打一片（扇形齐射） | `bhv_projectile` | `count_base=3~7`, `spread_deg=15~60` | `projectile` |
| 打中后跳到下一个目标 | `bhv_projectile` | `chain_count=2~5` | `projectile` |
| 穿透继续飞 | `bhv_projectile` | `pierce=1~3` | `projectile` |
| 近身一刀 | `bhv_melee_swing` | `range=100~160`, `arc_deg=60~120` | `melee` |
| 以自己为中心爆一圈 | `bhv_aoe_burst` | `radius=100~180`, `delay=0.2~0.5` | `aoe` |
| 延迟砸地（可预判） | `bhv_aoe_burst` | `delay=0.5~1.2` | `aoe` |
| 持续喷/持续烧 | `bhv_channel` | `max_channel_time=1.5~3`, `tick_interval=0.2~0.4` | `channel` |
| 召一个帮手打架 | `bhv_summon` | `max_count=1~4`, `lifetime=8~20` | `summon` |
| 冲过去撞人 | `bhv_dash` | `distance=250~450`, `speed=900~1400` | `movement` |
| 给自己上增益 | `bhv_buff_self` | `buff_mods`, `duration=4~10` | `buff` |

### 1.5 什么时候才允许新增行为

只有同时满足三条才提：

1. 想要的形态在表里**完全无法近似**（例：链式地雷、图腾继承施法者属性且能攻击）；
2. 不是"参数调不出来"，而是"结算结构不同"；
3. 已经向人类说明代价（新增 `.gd` + 注册表 + 行为测试 + 至少 1 个内容样例）。

**新增行为的流程写在《施工规格》§10，本文不重复。** 默认答案永远是"用现有七种拼"。

## 2. 设计模式库（18 个模式 / 6 组）

> 每个模式都是从「机制结构」层面提炼的，**不含任何原作技能名与数值**。
> 卡片格式：机制 → 行为 → 标签 → 参数 → 辅助挂法 → 平衡风险。
> 参数的「区间」取自首批 8 个主动的实测值（§4.1），不是硬约束，但偏离太多需要理由。

### A 组 · 投射类

**A1 单体穿刺**
机制：一发直线弹体，命中即结算，靠高单发伤害与高速度打点。
行为 `bhv_projectile`｜标签 `attack/spell` + `projectile` + 单元素
参数：`count_base=1` `speed=550~900` `radius=12~16` `lifetime=1.5~2.5` `spread_deg=0~8`
辅助：穿透、投射物速度、元素专注
风险：单体技能若 DPS 追平范围技，范围技就失去意义 —— 单体 DPS 应高 30~60%。

**A2 扇形齐射**
机制：一次多发，按 `spread_deg` 均分角度，贴脸全中、远距离散开。
行为 `bhv_projectile`｜标签 + `projectile`
参数：`count_base=3~7` `spread_deg=15~60`（`count=1` 时 `spread_deg` 被忽略）
辅助：多重投射（`behavior_overrides` 加 `projectile_count`，同时抬 `cost_multiplier`）
风险：多发 × 穿透 × 连锁是三重乘区，极易超模；`cost_multiplier` 必须跟着抬。

**A3 连锁跳跃**
机制：命中后按 `chain_count` 依次跳向附近目标，每跳衰减。
行为 `bhv_projectile`｜标签 + `projectile`
参数：`chain_count=2~5` `speed=500~800`
辅助：连锁反应（`chain_count` 加算）
风险：敌群越密收益越高，Boss 战几乎无用 —— 这是它的定价依据，不要额外补单体伤害。

**A4 抛射爆裂**
机制：弹体飞到落点后爆开，命中区加一圈范围伤害。
**当前实现有边界**：引擎没有「飞行→落地→爆炸」这种一次性行为，只能用两种近似之一：
- 单 part：`bhv_projectile` + 较大的 `radius`（命中即范围，视觉上是穿体爆炸）；
- 双 part：part1 `bhv_projectile`（飞行）+ part2 `bhv_aoe_burst`（**同帧结算**，不是落地才炸）。
若设计要求真正的引信/落点爆炸 → 走 §1.5 提「新行为」，不要自己加字段。
参数：`speed=400~700` `radius=60~110` `lifetime=0.6~1.2`
辅助：范围放大、点燃附加
风险：飞行时间就是玩家的预判窗口，`lifetime` 太短会变成"贴脸技能"，太长会打不中移动目标。

### B 组 · 近战类

**B1 横扫**
机制：身前扇形，一次结算全部命中目标。
行为 `bhv_melee_swing`｜标签 `attack` + `melee` + 元素
参数：`range=110~160` `arc_deg=70~120`
辅助：近战专注、范围放大、暴击
风险：`arc_deg > 180` 等于全屏，近战就失去了"贴身"的代价结构。

**B2 砸地**
机制：定点延迟爆炸，可以有前摇（`delay`），落点即伤害中心。
行为 `bhv_aoe_burst`｜标签 `attack` + `melee`（或 `aoe`）+ 元素
参数：`radius=90~150` `delay=0.35~0.8`
辅助：范围放大、击晕类（若将来有击晕 stat）
风险：`delay` 是"可被躲开"的补偿，`delay=0` 时应当降低伤害或缩小范围。

**B3 突进**
机制：位移 + 沿途伤害，兼作保命手段。
行为 `bhv_dash`｜标签 `attack` + `movement`
参数：`distance=250~450` `speed=900~1400` `path_damage={}`（**存在即启用**，内部键当前未被解析）
辅助：位移类（若有）、暴击
风险：位移技能天然自带"免伤窗口"，伤害必须低于同 CD 的纯输出技能 30% 以上。

### C 组 · 区域与持续类

**C1 瞬发新星**
机制：以自身为圆心瞬间爆发，清贴身怪。
行为 `bhv_aoe_burst`｜标签 `spell` + `aoe` + 元素
参数：`radius=110~160` `delay=0~0.35` `hit_count=1`
辅助：范围放大、元素专注
风险：零延迟 + 大范围 = 无脑解场。`delay` 与 `radius` 至少要有一个付出代价（CD ≥ 2s）。

**C2 延迟引爆**
机制：先落一个"定时器"（`delay=0.8~1.5`），到点才爆，配合聚怪使用。
行为 `bhv_aoe_burst`
参数：`delay=0.8~1.5` `radius=100~140` `hit_count=1~3`
辅助：持续时间、范围放大
风险：延迟越长，数值应越高（风险回报）；但**不能与"必定命中"共存**，否则就是纯白给。

**C3 持续光束**
机制：引导期间按 `tick_interval` 连续结算，移动会中断。
行为 `bhv_channel`｜标签 `spell` + `channel` + 元素
参数：`max_channel_time=1.5~3` `tick_interval=0.2~0.4`
辅助：施法速度（影响 tick 密度）、持续时间
风险：tick 越密，DPS 越难手算；**必须保证 `tick_interval × tick_count ≈ max_channel_time`**，否则会出现"引导结束了还在打"或"引导结束前就停"。

**C4 地面残留**
机制：打出一片持续区域，敌人进入就吃伤害（用 `bhv_aoe_burst` + `hit_count` + 较长 `delay` 近似）。
参数：`radius=90~140` `delay=0.5~1.0` `hit_count=2~4` `hit_interval=0.4~0.8`
辅助：持续时间、范围放大
风险：多段命中会让"命中数"统计失真，巡检时要按 `hit_count` 折算 DPS。

### D 组 · 召唤与放置类

**D1 随从编队**
机制：召唤多个单位持续作战，本体退化为指挥位。
行为 `bhv_summon`｜标签 `spell` + `summon`
参数：`max_count=2~4` `lifetime=8~20`
辅助：随从伤害/生存（当前用 `minion_damage` / `minion_life` / `minion_attack_speed`）
风险：随从继承的是**白名单三项**（§8.2），不是全部 stats；想给随从"元素抗性"得先扩 `MinionRegistry.INHERIT_STATS`。

**D2 单一强仆**
机制：只召 1 个高质量单位，兼坦兼输出。
行为 `bhv_summon`
参数：`max_count=1` `lifetime=15~30`
辅助：随从伤害
风险：`max_count=1` 时"顶掉最旧"的语义会变成"重复施法白扣蓝"，UI 需要提示"已存在"。

**D3 图腾/哨塔**
机制：放一个不动但持续输出的单位，等价于"可被摧毁的炮台"。
行为 `bhv_summon`（`max_count=1~2`，`lifetime=8~15`）
标签 `spell` + `summon`（**不要**加 `totem` —— 该标签未注册）
风险：当前没有"图腾继承施法者属性"的专项机制，等价能力靠随从继承白名单；若设计要求强绑定，先提需求，不要自己加字段。

### E 组 · 增益与控制类

**E1 自身增益**
机制：给自己挂一组修饰符，持续 `duration` 秒。
行为 `bhv_buff_self`｜标签 `spell`/`attack` + `buff`
参数：`buff_mods` 是**数组**，每项 `{&"stat": …, &"op": 0|1|2, &"value": …}`（`op`：0=`FLAT_ADD` 加值、1=`INCREASED` 加算%、2=`MORE` 乘算%）；`duration=4~10`

```gdscript
&"buff_mods": [{
&"stat": &"physical_damage",
&"op": 1,
&"value": 30.0
}],
&"duration": 5.0
```

辅助：持续时间、增益强度（当前无专用 stat，需先加）
风险：① 增益是乘区叠加，两个 +40% 不是 +80%，上线前必须算组合极值；② 施放时按**新的 `source_id`** 挂载，重复施放会叠加而不是刷新 —— `duration` 必须小于 `base_cooldown`，否则自己就能叠 buff。

**E2 诅咒降抗**
机制：给敌人挂一个减抗 debuff。**当前引擎没有 debuff 容器**，只能用 `bhv_aoe_burst` 的伤害 + 高 `damage_effectiveness` 近似。
风险：真正的降抗需要"敌方 stats"这一层，属于架构缺口 —— **遇到就停下来提需求，不要用假的 stat 硬凑**。

**E3 光环/领域**
机制：持续存在的范围增益。当前只能做成 `bhv_buff_self` + 较长 `duration` + 手动续。
风险：没有"保留资源"机制；若设计需要常驻光环，先提"保留"需求。

### F 组 · 触发类

**F1 命中触发**
机制：A 技能命中时自动释放 B 技能。
实现位置：**不在 `.tres` 里**，走 `TriggerData`（`content/gems/triggers/`）+ `TriggerManager`。
参数：`event` / `chance` / `cooldown` / `linked_slot_index`（**目标槽**，不是触发源槽，见 P-22）
风险：限流公式是 `min(事件率×chance, 1/cd)`（§7.2），堆触发次数收益会突然归零 —— 这是设计特性，不是 bug。

**F2 条件触发**
机制：低血/被击/暴击等条件满足时触发。
实现：`TriggerData.event` 换事件源。**与 F1 共用同一套限流**。
风险：条件越容易满足，等效 DPS 越高；必须用限流压住。

## 3. 辅助宝石设计法

### 3.1 从"效果类型"到"四个口子"的映射

外界资料里辅助宝石分五类效果，落到本项目只有四个口子（第五个 `conditions` 暂缓，见 D-15）：

| 效果类型 | 例子 | 本项目落点 | 写法 |
|---|---|---|---|
| 改数值（增伤/加速/降耗） | 元素增伤、施法加速 | `stat_modifiers` | `ModifierSpec`，`source_id = support_id` |
| 改数量/形态（多投/连锁/穿透） | 多重投射 | `behavior_overrides` | `{&"projectile_count": {&"add": 2.0}}` |
| 改可搭配范围（标签） | 元素专注、近战强化 | `require_tags` / `exclude_tags` / `add_tags` | 三元组 |
| 改施法主体/模式 | 图腾化、触发化 | `behavior_overrides` 或 `TriggerData` | 能不用新字段就不用 |
| 按条件生效 | "仅对初始技能" | ❌ 暂缓（口子 4） | 不要自己接 |

### 3.2 八个辅助原型

| 原型 | 效果 | 写法 | 代价（必须给） |
|---|---|---|---|
| P1 数量 | 投射物 +N | `behavior_overrides` → `projectile_count` add | `cost_multiplier` 1.3~1.5 |
| P2 穿透 | 穿透 +N | `behavior_overrides` → `pierce` add | `cost_multiplier` 1.15~1.3 |
| P3 连锁 | 连锁 +N | `behavior_overrides` → `chain_count` add | `cost_multiplier` 1.3~1.4 |
| P4 范围 | 范围 × | `stat_modifiers` → `area_size` MORE 或 INCREASED | 同组减伤（`damage` 负向）或抬耗 |
| P5 元素专注 | 单元素增伤 | `stat_modifiers` → `<el>_damage` INCREASED | `exclude_tags` 排掉其他元素技能 |
| P6 暴击 | 暴击率/倍率 | `stat_modifiers` → `crit_chance` / `crit_multi` | 抬耗，或 `flags` 加 `cannot_crit` 互斥项 |
| P7 速率 | 施法/攻击加速 | `stat_modifiers` → `cast_speed` MORE | 抬耗 |
| P8 代价换强度 | 强力增益但有副作用 | `stat_modifiers` 正向 + `cost_multiplier` 显著抬 | **必须有副作用**，否则是纯白给 |

**所有"增加能力"的辅助都必须有代价**。当前引擎能表达的代价只有三种：抬耗（`cost_multiplier`）、加标签限制（`exclude_tags`）、改 flags。若你想要"降低移速""减少生命"这类代价，属于新 stat —— 先提需求。

### 3.3 兼容性三元组：三个常见错误

```gdscript
require_tags = [&"projectile"]   # 必须全部具备，缺一不兼容
exclude_tags = [&"melee"]        # 命中任一即不兼容
add_tags = [&"aoe"]              # 装配后给技能追加标签
```

| 错误 | 后果 | 正确做法 |
|---|---|---|
| `require_tags` 写成 `[&"projectile", &"fire"]` 想表达"或" | 实际是"且"，只有火系投射物能用 | 要做"或"就拆成两颗辅助 |
| 写了 `require_tags` 但没写 `exclude_tags` | 该辅助可能挂到不该挂的技能上 | 至少排掉最明显的反例（如法术专用就 `exclude_tags=[&"attack"]`） |
| `add_tags` 加了 `aoe` 但没写 `aoe` 行为的参数 | 装配成功但表现不变，玩家以为没生效 | `add_tags` 必须同时改 `behavior_overrides` 或参数，否则毫无意义 |

**改 `add_tags` 前必须问自己**：加了标签以后，会不会让另一颗辅助突然也能挂上来？标签是会传染的兼容性开关。

### 3.4 冲突与独占

`conflicts_with` 必须**双向一致**：A 写了 B，B 必须写 A。单向冲突会变成"先镶谁决定结果"，玩家可以绕过（台账 §16.3 第 7 条）。

```gdscript
# support_cold_focus.tres
conflicts_with = Array[StringName]([&"support_fire_focus"])
# support_fire_focus.tres 里必须有：
conflicts_with = Array[StringName]([&"support_cold_focus"])
```

### 4.2 区间护栏（偏离需理由）

| 字段 | 建议区间 | 越界后果 |
|---|---|---|
| `base_cost` | 6 ~ 25 | < 4 无资源压力；> 30 需配套回蓝机制 |
| `base_cooldown` | 0 ~ 8 | 0 表示可连发，此时必须靠耗魔限速 |
| `base_cast_time` | 0.35 ~ 1.2 | < 0.3 手感虚浮；> 1.5 站桩挨打 |
| `damage_effectiveness` | 0.6 ~ 1.4 | 是"附加伤害"的缩放，不是强度旋钮，别拿它配平 |
| `radius` | 60 ~ 180 | > 200 半个屏幕，近战失去代价结构 |
| `speed`（投射） | 400 ~ 900 | < 300 追不上移动目标；> 1100 看不出轨迹 |
| `arc_deg`（近战） | 60 ~ 140 | > 180 等价全屏 |
| `max_count`（召唤） | 1 ~ 4 | `HARD_CAP=64` 兜底，但 UI 与性能都撑不住 > 8 |

### 4.3 等级曲线怎么选

`GemLevelScaling` 两个模式（§3.1）：

| 想要的手感 | 配法 |
|---|---|
| 全程平滑成长（默认） | `per_level = 0.1`，不设 `knee_level` |
| 前期强、后期乏力（开荒技） | `per_level = 0.16`、`knee_level = 8`、`per_level_late = 0.04` |
| 前期弱、后期爆发（成型技） | `per_level = 0.04`、`knee_level = 10`、`per_level_late = 0.2` |
| 到某级封顶（工具技） | `per_level = 0.12`、`knee_level = 10`、`per_level_late = 0.0` |

`knee_level = 0` 时 `per_level_late` 被完全忽略。20 级总倍率建议落在 **2.0 ~ 4.0**。

### 4.4 两条判据（写完必须算）

1. **单位化耗资** = `base_cost / base_cooldown`（无 CD 时用 `/ base_cast_time`）。8 个技能放在一起比，谁明显低谁就是"能无限放"的隐患。
2. **DPS 极差** = 最高 DPS ÷ 最低 DPS。**> 2.5 倍即视为超模**，不必等玩家反馈。

## 5. 命名与文案

### 5.1 三条规则（规格 §15）

1. 不用单词型技能名（一个英文单词就当一个名字）；
2. 不用 `Awakened / Vaal / Mirror / Atlas / 6-Link` 这类专有体系词；
3. 中文名以「材质+形态」或「动作+结果」两段式为主。

### 5.2 词根表（组合生成，不撞名）

| 类别 | 词根 |
|---|---|
| 材质/元素 | 霜 · 炎 · 雷 · 铁 · 骨 · 影 · 血 · 星 · 尘 |
| 形态 | 矛 · 刃 · 环 · 域 · 潮 · 柱 · 链 · 巢 · 印 |
| 动作 | 贯穿 · 迸发 · 回响 · 缠绕 · 撕裂 · 坠落 · 凝结 · 灼烧 |
| 修饰 | 初阶 · 裂变 · 恒久 · 双生 · 余烬 · 低语 |

组合示例：`霜矛`（材质+形态）、`雷光斩`（材质+动作）、`蚀骨引线`（动作+形态）、`烈焰爆发`（材质+动作）。

**判定是否撞名**：把中文名转成两段，逐段在 `grep -r display_name content/` 里查重叠；两段全同才算撞名，单段相同可接受。

### 5.3 文案模板

**技能描述**（一句话，写"做什么"不写数字）：

```
<动作>，对<范围>内的敌人造成<元素>伤害，并<附加效果>。
```

例：`掷出一支凝霜长矛，命中后炸开寒气，使周围敌人持续受冻。`

**辅助描述**（写"改变什么"，必须暗示代价）：

```
使技能<增强点>，但<代价>。
```

例：`使投射物数量增加，但魔力消耗显著提高。`

**一句话卖点**（给 UI 用，≤ 12 字）：`贴脸清场`、`远程点杀`、`越打越强`。

## 6. 从模式到 `.tres`

### 6.1 手写 `.tres` 的六条硬规则

1. **必须用 `[gd_resource type="Resource" script_class="SkillData" format=3]` 开头**，`script_class` 少了会加载成裸 Resource。
2. **每个脚本各占一个 `ext_resource`，id 唯一**（`1_xxx` / `2_xxx`）。同一个脚本被两个字段用到时**复用同一个 id**，不要写两份。
3. **字典键用 `&"xxx"`**（`StringName`），值写数值。`tags` 必须写成 `Array[StringName]([&"a", &"b"])`，不是 `["a","b"]`。
4. **`parts` 必须写成 `Array[ExtResource("2_xxx")]([SubResource("...")])`**，类型标注不能省。
5. **嵌套资源（`GemLevelScaling`、`SkillPart`）用 `[sub_resource]`**，并在主资源里以 `SubResource("id")` 引用。
6. **`behavior_params` 的键必须是行为层真实读取的键**（§1.1 表）。拼错的键不会报错，只会静默失效（P-06）。

### 6.2 完整示例：新增「连锁冰弹」

模式 A3（连锁跳跃），攻击系冰伤投射，三连锁。

```gdscript
[gd_resource type="Resource" script_class="SkillData" format=3]

[ext_resource type="Script" path="res://mods/jes-skills/systems/skills/data/gem_level_scaling.gd" id="1_scale"]
[ext_resource type="Script" path="res://mods/jes-skills/systems/skills/data/skill_part.gd" id="2_part"]
[ext_resource type="Script" path="res://mods/jes-skills/systems/skills/data/skill_data.gd" id="3_skill"]

[sub_resource type="Resource" id="Scaling_chain_ice"]
script = ExtResource("1_scale")
per_level = 0.12

[sub_resource type="Resource" id="Part_chain_ice"]
script = ExtResource("2_part")
base_damage = {
&"cold": 82.0
}
behavior_id = &"bhv_projectile"
behavior_params = {
&"chain_count": 3,
&"count_base": 1.0,
&"lifetime": 1.8,
&"radius": 13.0,
&"speed": 680.0,
&"spread_deg": 0.0
}

[resource]
script = ExtResource("3_skill")
gem_id = &"frost_chain"
display_name = "霜链"
parts = Array[ExtResource("2_part")]([SubResource("Part_chain_ice")])
tags = Array[StringName]([&"attack", &"projectile", &"cold"])
base_cost = 11.0
base_cooldown = 0.9
base_cast_time = 0.45
level_scaling = SubResource("Scaling_chain_ice")
```

**为什么这么配**：

- `chain_count = 3` 写在 params 里作为 base；辅助宝石再 `add` 就是叠加，不是覆盖。
- `base_cost 11` 比霜矛（10）高 10%：连锁在群体场景收益明显，得付一点钱。
- `base_cooldown 0.9`：连锁技能若可无限连发，清屏效率会失控。
- `per_level 0.12`：略高于基准 0.1，因为它是"中期成型"定位。

## 7. 反例库（照着做就会返工）

| # | 反例 | 为什么错 | 正确做法 |
|---|---|---|---|
| 1 | 为了一个技能在 `skill_executor.gd` 里加 `if gem_id == &"xxx"` | 策略写进代码，附录 C 第 1 条直接违反 | 改数据，或提出"新行为"需求 |
| 2 | `behavior_params` 写 `projectile_count` 想控制发数 | 被 `_stat_value` 忽略，只有 `count_base` 有效 | 写 `count_base` |
| 3 | 辅助宝石只加 `add_tags`，不改任何参数 | 装配成功但表现不变，玩家以为 BUG | 加标签必须配套改参数 |
| 4 | 两颗辅助互相冲突但只写单向 | 先镶谁决定结果，可被绕过 | 双向写 `conflicts_with` |
| 5 | 用 `damage_effectiveness` 当强度旋钮配平 | 它是"附加伤害缩放"，改它等于改管线语义 | 用 `base_damage` 与 CD/耗魔配平 |
| 6 | DoT 技能给 `HIT` 通道，靠"高伤害"表现持续伤害 | 会吃到 hit 加成，G9 通道隔离失效 | `damage_channel = 2` |
| 7 | 新辅助没写代价（不抬耗、不限标签） | 纯白给，必然超模 | 至少给一种代价（§3.2） |
| 8 | 技能名直接用英文单词 | 撞 IP 风险 + 违反 §15 | 用词根表组合中文名 |
| 9 | 给召唤物加元素抗性词缀 | 随从只继承白名单三项，加了不生效 | 先扩 `INHERIT_STATS` 并说明代价 |
| 10 | 数值全靠 `per_level` 拉，不看 CD/耗魔 | 前期就能无限放 | 算单位化耗资（§4.4） |
| 11 | 新增 `.tres` 后不改内容数量断言，或改成 `>= N` | 失去"防止内容丢失"的意义（P-23） | 改断言并写明依据 |
| 12 | 看到 `conditions` 字段缺失就自己加上 | D-15 明令暂缓，接线要 4 步且改 `cache_key` | 停下来提需求 |

## 1. 先划边界：引擎现在能做什么、不能做什么

这一节是整份规划的**前提**。不先钉死，后面所有数值都是空谈。

| 想做的效果 | 代码现状（已实地核对） | 本批结论 |
|---|---|---|
| 真正的持续伤害（点燃 / 中毒 / 流血） | 伤害通道的分类里有「持续伤害」这一项，持续伤害的计时器机制也在；但**伤害包结构里没有「通道」这个字段**，也没有任何技能真的接上去 | **不做**。硬写「持续伤害」通道，只会让增伤词缀对它失效，是纯亏 |
| 敌方减益（减抗 / 减速 / 易伤 / 破甲） | 敌人没有属性容器，也没有负面状态容器（手册 E2 已标注） | **不做**。不拿假属性硬凑，凑出来的东西不生效 |
| 治疗 / 护盾 / 自伤换强度 | 没有治疗接口；「以生命为代价」的消耗类型虽然在字段里声明了，但沙盒只扣蓝 | **不做**。生存只走「护甲 / 抗性 / 位移」三条真杠杆 |
| 无敌帧 | 没有 | **不做**。位移的收益是「真的离开弹道」，不是免伤 |
| 护甲减伤 | 减伤率 = 护甲 ÷（护甲 + 10 × 本次物理总伤），护甲系数固定为 10 | **做**，但数值必须按这个公式配，见第 7 节 |
| 元素抗性 | 直接按百分比减伤，**上限 75%** | **做**，注意后期可能触顶 |

> **依据（代码位置）**：`systems/skills/skill_channel.gd`（通道分类）、`systems/skills/combat/damage_packet.gd`（伤害包，确认无通道字段）、`systems/skills/combat/damage_calculator.gd` 第 15–16、67–78 行（护甲系数与抗性上限）、`systems/skills/combat/health_component.gd`（无治疗）、`sandbox/sandbox_main.gd`（只有扣蓝路径）。

## 2. 设计原则

### 2.1 好玩假设

> **同一个按键的收益，取决于你站在哪、什么时候按。**

每次施法都是在**站位**和**时机**上押注，而不是在等冷却。所以本批技能全部带「条件收益」：距离条件（贴脸 / 成线）、时机条件（预判 1.2 秒后的落点）、位置条件（圈里停留要不要付代价）。**没有一个技能是「按了就变强」的纯数值按钮。**

### 2.2 三条支柱

1. **一个技能只押一个决策。** 禁止两个技能争同一个决策，否则永远只有一个能用。
2. **不抬伤害天花板，只换效率形态。** 霜矛 200 是上限，新增技能靠「对群 / 贴脸 / 预判」换效率，不靠更高数值。
3. **防御与状态的收益必须在 3 秒内能被感知。** 感知不到的防御等于没有。所以防御窗口全部不短于 3.5 秒，持续时间都要在界面上看得见。

### 2.3 定价规则（为什么这些数字不是拍脑袋）

- **耗蓝**：沙盒法力上限 200 点、每秒回蓝 20 点。所以单个技能的「蓝耗 ÷ 冷却」必须小于 20，否则自己就把自己耗干。
- **冷却**：与「施法前摇 + 判定延迟」联动。前摇越长，冷却越短——因为已经用时间付过代价了。
- **伤害**：按「每秒伤害 = 总伤害 ÷ 冷却」定档，四档互相不越界（见第 4 节表）。

## 4. 伤害向 4 个

### 4.1 总表

| 编号 | 技能 | 行为 | 标签 | 关键参数 | 伤害 | 耗蓝 | 冷却 | 前摇 | 每秒伤害 |
|---|---|---|---|---|---|---|---|---|---|
| D1 | 裂石重击 | 近战挥砍 | 攻击 · 近战 · 物理 | 射程 **150**、扇角 **70°** | 物理 170 | 16 | 1.4 秒 | **0.85 秒** | 121 |
| D2 | 贯空箭 | 投射物 | 攻击 · 投射物 · 物理 | 速度 900、存活 2.5 秒、**穿透 3 次** | 物理 100 | 12 | 0.9 秒 | 0.45 秒 | 111 单体 / **444** 满穿 |
| D3 | 熔核引爆 | 范围爆发 | 法术 · 范围 · 火焰 | 半径 **170**、延迟 **1.2 秒** | 火焰 380 | 22 | 3.2 秒 | 0.7 秒 | 119 |
| D4 | 星屑连射 | 投射物 | 法术 · 投射物 · 闪电 | **5 发**、散角 36°、存活 **1.1 秒** | 闪电 38 × 5 | 18 | 1.2 秒 | 0.4 秒 | **158** 贴脸 / 32 远距 |

### 4.2 每个技能的定价理由

**D1 裂石重击 —— 唯一「慢而重」的近战**
- 现有雷光斩是 90° 宽扇、射程 130、150 伤害、可 3 连。所以 D1 的差异必须做在**形状**上，不能做在数值上：**70° 窄扇 + 射程 150 + 0.85 秒前摇**。
- 窄 20° 意味着必须站正对，0.85 秒前摇意味着「挥出去就收不回来」。170 伤害 ÷ 1.4 秒 = 每秒 121，**低于雷光斩的 150**——因为它不需要管理充能，代价换成了站位精度。
- 一句话决策：**敢不敢贴到 150 以内，正对着挥**。

**D2 贯空箭 —— 唯一「成线」的技能**
- 穿透 3 次在代码里的语义是「命中后余量减 1，余量 ≤ 0 才回收」，所以**穿透 3 次 = 可以命中 4 个目标**（`projectile_field.gd` 第 217–220 行）。
- 只打一个目标时每秒 111 是**故意做低**的（打单体它不如霜矛），但把敌人排成一条线时是 444。它的价值完全取决于「你会不会站位拉线」。
- 蓝耗可持续性：0.9 秒冷却 + 12 蓝 = 每秒 13.3 蓝。

**D3 熔核引爆 —— 延迟档的第三级**
- 现有延迟档：霜爆 0.35 秒 / 半径 130 → 烈焰 0.5 秒 / 半径 100。本批补 **1.2 秒 / 半径 170**，形成「半径越大、延迟越长」的清晰梯度，玩家能一眼算出「这发赌不赌」。
- 380 火焰伤害 ÷ 3.2 秒 = 每秒 119，是**单段最高伤害**，但 1.2 秒内敌人会走开。命中率就是它的真实成本。

**D4 星屑连射 —— 唯一「必须贴脸」的投射技能**
- 5 发 × 36° 散角 + 1.1 秒存活（速度 950，射程上限约 1045）。
- **几何实话**：5 发的角度分配是 **−18° / −9° / 0° / +9° / +18°**（`skill_executor.gd` 第 89–90 行）。按弹丸半径 8、目标半径约 25 估算，能命中的距离上限约为「33 ÷ 该角度的正弦值」：最外侧 18° 方向约 **107 距离**，9° 方向约 **211 距离**。也就是说：
  - **约 110 距离内**：5 发全中，每秒 158（高于 D1 的 121）
  - **约 210 距离内**：命中 3 发，每秒 95
  - **更远**：只剩中间 1 发，每秒 32
- 这就是「必须贴脸」的严格版本，不是修辞。若你复审后觉得太苛刻，有两个可调旋钮：散角 36° 收到 24°（全中窗口翻倍），或存活 1.1 秒加到 1.4 秒（射程延长，但远距依旧脱靶）。**我默认建议不动**，因为它的定位就是高风险高回报。
- 技术备注（给执行方）：投射物数量走整数聚合，基础值写在「数量基数」字段上，与霜矛的写法一致。

## 5. 生存向 4 个

### 5.1 总表

| 编号 | 技能 | 行为 | 标签 | 效果 | 耗蓝 | 冷却 | 窗口 |
|---|---|---|---|---|---|---|---|
| S1 | 磐石架势 | 自身增益 | 法术 · 增益 · 物理 | 护甲 **+450**、物理抗性 **+10** | 12 | 8 秒 | 5 秒 |
| S2 | 元素壁障 | 自身增益 | 法术 · 增益 | 火 / 冰 / 雷抗 **+30**、混沌抗 **+15** | 14 | 7 秒 | 5 秒 |
| S3 | 影缝闪避 | 冲刺 | 攻击 · 移动 · 物理 | 位移 **260**、速度 1300、**无伤害** | 8 | **2.0 秒** | 0.2 秒完成 |
| S4 | 破阵翻滚 | 冲刺 **+** 自身增益（两段） | 攻击 · 移动 · 物理 | 位移 **240** + 护甲 **+260**，持续 3.5 秒 | 12 | 5 秒 | 3.5 秒 |

### 5.2 每个技能的定价理由

**S1 / S2 —— 同一杠杆的两个刻度（物理 vs 元素）**
- 这不是重复，是**针对不同威胁的两种答案**。差异由「敌人的伤害构成」决定，不由数值决定。
- **前提条件（对上层玩法的依赖，必须标出来）**：敌人设计里物理伤害与元素伤害的占比都要不低 30%。若某一类占比低于 15%，对应的那个技能会退化成废牌。这条**不归本批决定**，取决于敌人表。
- 蓝耗效率：磐石架势每秒 1.5 蓝，元素壁障每秒 2 蓝。近乎免费，因为它们不产出伤害，真实成本是**占用一个技能槽**。

**S3 影缝闪避 —— 把位移当闪避键**
- 冷却 2.0 秒，是全批最短的。它存在的意义是给「不想带防御增益」的玩家一个高频的生存手段。
- **诚实说明**：没有无敌帧。它的收益是「真的离开了那条弹道」，对追踪型、持续型伤害无效。这个限制必须写进技能描述，否则玩家会觉得「闪了还是被打」是程序错误。
- 伤害为 0（不带路径伤害）。这与暗影冲刺形成清晰分工：暗影冲刺是「位移 + 顺手打一下」，影缝闪避是「纯位移、更快更频」。

**S4 破阵翻滚 —— 位移 + 兜底减伤**
- 两段：先冲刺 240 距离，再挂护甲 +260 持续 3.5 秒。
- 顺序说明：位移段在前，因为减伤窗口是给「落地之后」用的，不是给位移过程用的。
- 与磐石架势的差异：磐石架势是纯防御（450 护甲，但不位移），破阵翻滚是「边跑边扛」（260 护甲 + 240 位移）。两者叠加到 710 护甲是**允许的**，代价是两个槽 + 20 蓝。

### 6.1 总表

| T2 | 猎杀号令 | 自身增益 | 攻击 · 增益 | 暴击率 **+20**、暴击伤害 **+40** | 16 | 7 秒 | 5 秒 |
| T3 | 战地工事 | 范围爆发 **+** 自身增益 | 法术 · 范围 · 混沌 | 3 段 × 0.7 秒（每段 22）+ 护甲 **+180** | 18 | 5 秒 | 1.4 秒判定 + 4 秒减伤 |
| T4 | 长明烛火 | 自身增益 **+** 召唤 | 法术 · 召唤 · 物理 | 先强化随从，再召 1 只存活 20 秒 | 16 | 8 秒 | 随从 20 秒 |

### 6.2 每个技能的定价理由

**T1 裂地余震 —— 卖「停留成本」**
- 4 段 × 26 伤害，段间隔 0.7 秒，判定窗合计约 2.1 秒。它不减速（引擎没这个能力），所以收益完全来自「你敢不敢站在里面继续打」。
- 总伤 104 ÷ 4.5 秒 = 每秒 23，是全批最低的伤害向数值。它卖的不是伤害，是**区域拒止**。
- 段数机制依据：范围爆发行为自带「段数」与「段间隔」两个参数，沙盒里的多段判定已经实现，不是本批新增机制。

**T2 猎杀号令 —— 唯一「暴击窗」**
- 暴击率 +20（加法，单位是百分点）、暴击伤害 +40（增量百分比，作用在基础 150% 之上）。
- 它不直接产出伤害，收益取决于**你在 5 秒里打出了多少次命中**。所以它与星屑连射（5 发）、贯空箭（穿透多目标）天然联动——这是本批唯一一组「技能互相加成」的设计，但**不构成强制组合**，单独用也有收益。
- 定价理由：16 蓝 ÷ 7 秒 = 每秒 2.3 蓝，很便宜，但占一个槽 + 占一个 5 秒窗口。

**T3 战地工事 —— 「圈地 + 站桩」**
- 3 段混沌 22 + 护甲 +180 持续 4 秒。它是裂地余震与磐石架势的**杂交**，但杂交本身就是它的定位：适合「我要在这个点守 4 秒」的场景。
- 数值上两项都不如专精（每秒 13 < 23；护甲 180 < 450），这是杂交应有的代价。
- 用混沌元素是为了补全元素覆盖面（现有混沌伤害只有蚀骨引线一个）。

**T4 长明烛火 —— 随从强化器**
- **两段的顺序必须是「先强化、后召唤」**。依据：随从在**召唤那一刻**拷贝施法者的三项属性（随从伤害、随从攻速、随从生命），见 `minion_registry.gd` 第 16 行。写反就是白给。
- 强化持续 7 秒，随从存活 20 秒。**拷贝之后强化过期，不影响已经召出来的随从**（属性已经复制过去），这是机制的必然结果，不是程序错误。
- 它让灵魂召唤从「多个肉盾」变成「一个强输出」，是路线选择而非数值升级。

| T3 战地工事 | 13 | 3.6 | 通过 |
| S1–S4、T2、T4 | 0 | 1.5–4.0 | 通过（近乎免费） |

**组合压力测试**：裂石重击 + 星屑连射同时按 = 每秒 26.4 蓝 > 20，会耗干。**这是故意的**——不能全带输出向。带两个输出 + 一个防御（+1.5）仍是 27.9，依然超；说明 200 点的蓝池是「应急缓冲」而不是「无限续航」，玩家必须取舍。

### 7.2 护甲收益（按真实公式算，不是估）

减伤率 = 护甲 ÷（护甲 + 10 × 本次物理总伤）

| 组合 | 护甲 | 挨 100 点物理 | 挨 40 点物理（小怪） |
|---|---|---|---|
| S4 破阵翻滚 | 260 | **20.6%** | 39.4% |
| T3 战地工事 | 180 | **15.3%** | 31.0% |
| S1 磐石架势 | 450 | **31.0%** | 52.9% |
| S1 + S4 | 710 | **41.5%** | 64.0% |
| S1 + S4 + T3 | 890 | **47.1%** | 69.0% |

**结论**：磐石架势的 450 点是「一击减三成」，不是「减一半」。这个量级是对的——如果 450 点就能减 70%，防御技能会变成必带。小怪伤害低时收益虚高（53%），这是护甲公式的固有特性，**不是本批能修的**（要修得改公式，属于架构变更）。

### 7.3 抗性收益

- 元素壁障给火 / 冰 / 雷 +30% → 元素伤害乘 0.7；混沌 +15% → 乘 0.85。
- 上限 75%。若角色后期基础抗性已达 45%，元素壁障的 30 点会浪费一半。**这是已知风险**，处理方式是后期通过辅助宝石 / 装备调整，不在本批解决。

# 形态类辅助宝石 · 设计方案（供复审）

> **性质**：设计讨论稿，**没有改任何代码**。
> **问题**：想在辅助宝石里多一个类型，能修改技能的行为，比如把投射物变成环形环绕。这样好不好？有没有别的办法？
> **阅读约定**：正文全中文。只有必须写进文件的名字与代码位置保留英文，旁边都给中文；文末有对照表。

---

## 0. 先给结论

**方向是对的，业界有成熟先例。但你这句话里藏着三件成本差十倍的事，必须先拆开。**

| 你想要的 | 真实成本 | 我的建议 |
|---|---|---|
| 投射物变成**一圈打出去**（环形散射） | 很小，改四处判断即可 | **做**，这是本方案的第一档 |
| 投射物变成**绕着角色转**（真环绕） | 大，需要投射物学会圆周运动 | **做成一个独立技能**，不要做成辅助石 |
| 辅助石可以**把投射物换成范围爆发**（换行为类型） | 极大，且会毁掉技能身份 | **不做**，理由见第 3 节 |

一句话：**加「形态」这一维，不要加「换行为」这一类。** 前者是给技能换衣服，后者是给技能换人。

---

## 1. 三档拆分（这是整份方案的核心）

### 第一档：改「方向分布」——环形散射、交叉、随机

- **效果**：还是那个投射物，还是那个伤害，只是发射时**方向怎么摊开**变了。
- **现有接口**：辅助宝石的「行为覆盖」字段已经能改任意行为参数，写法是加法、乘法或直接赋值三种。所以 `spread_deg`（散角）现在就能被覆盖。
- **卡在哪**：现有的角度分配公式是**扇形，而且包含两个端点**——
  `角度 = −散角 ÷ 2 + 散角 × 第几发 ÷（总发数 − 1）`
  所以散角写 360° 时，5 发的角度是 −180、−90、0、90、180，**首尾两发完全重合**，实际只有 4 个方向，看起来是「缺一个口」的环。
- **需要什么**：一个「分布方式」参数，区分「扇形（含端点）」和「环形（等分，不含端点）」。
  - 扇形：`−散角 ÷ 2 + 散角 × 第几发 ÷（总发数 − 1）`
  - 环形：`360 × 第几发 ÷ 总发数`
- **改动量**：一个参数、四处判断（执行器里的角度分支）。**不是按技能名分支**，是按形态参数分支，符合「策略进配置表」的铁律。

### 第二档：改「运动轨迹」——真环绕、回旋、追踪

- **效果**：投射物不是飞出去就没了，而是绕着施法者转圈、或者飞出去再飞回来。
- **为什么贵**：现在的投射物是「出生 → 直线飞 → 撞到或超时回收」。要环绕就得有：
  - 圆心跟随施法者（施法者移动时环要跟着走）
  - 角速度而不是线速度
  - 存活时间结束后的统一回收
  - 与现有对象池、命中冷却、空间哈希的配合
- **结论**：这已经不是「辅助宝石」的粒度了，它是**一种新的行为**。建议直接做成一个技能（比如「环绕符文」），而不是让所有投射物技能都能变成环绕。

### 第三档：换「行为类型」——投射物变范围爆发、近战变投射物

- 这是你原话里最容易被理解成的那一种，也是我最不建议的。理由见第 3 节。

## 2. 业界是怎么划这条线的

| 作品 | 有没有「改形态」的辅助 | 具体做法 | 边界 |
|---|---|---|---|
| 流放之路 | **有，而且很典型** | 「箭雨新星」辅助把「向前射箭」改成「向天上射一支载荷箭，落地后**以落点为中心向四周环形射出**」 | 不能辅助引导技能、不能辅助召唤、不能辅助已经是空中箭的技能；并且带 **26%–40% 的伤害折扣** + 蓝耗倍率 150% |
| 流放之路 | 有 | 「齐射」辅助让投射物**并排**发射；「弹幕」辅助让投射物**依次**发射（改变时序而非方向） | 都带伤害折扣 |
| 暗黑破坏神 4 | 有，但归属不同 | 「技能专属威能」可以改技能行为，例如旋风斩定期把敌人拉过来、土击变成土系技能 | 社区长期批评：这类威能绑在装备上会让配装僵化、必带；**且都是技能专属，不是通用** |
| 流放之路（反例） | **没有** | 没有任何辅助宝石能把火球变成旋风斩 | 二十年没破这条线 |

**三条可以直接抄的结论**：

1. **改「发射方式」是合法设计**，玩家也认。
2. **改形态必须带代价**，否则必带。流放之路统一用「伤害折扣 + 蓝耗倍率」。
3. **改形态不等于换技能**。箭雨新星改完还是箭、还是投射物、还是同一套伤害计算，只改了「从哪发射、朝哪飞」。

## 3. 为什么我不建议做「能换行为类型」的辅助石

五条理由，按严重程度排：

1. **与现有立法冲突。** 规格第 6.1 节已经裁定「辅助宝石不得替换技能本体」，理由是换引用会连带炸冷却、兼容性、真源、存档。换行为类型是这个禁令的同一件事，只是换的是行为引用而不是数据引用。
2. **标签会和实际行为脱节。** 兼容性判定全部基于标签。一个带「近战」标签的技能被换成投射物行为后，标签还写着近战——后续所有按标签走的判定（词缀是否生效、辅助石是否兼容、触发条件）全部错位。
3. **行为参数不通用。** 投射物有 8 个参数（数量、速度、存活、半径、穿透、分叉、连锁、散角），范围爆发只有 4 个（半径、延迟、段数、段间隔）。换过去之后，原来那批参数变成垃圾数据，还得有人负责清理。
4. **平衡面会爆炸。** 8 个技能 × 7 种行为 = 56 种组合，每一种都要单独定价、单独写代价、单独测。这不是内容量的问题，是**测试和调参的工时**问题。
5. **没有先例。** 上面那张表里，二十年没人这么干，不是因为他们想不到。

---

## 4. 推荐方案：把「形态」做成辅助宝石的一个效果维度

### 4.1 参数设计

在行为参数里新增一个「分布方式」，两个取值就够覆盖你说的需求：

| 取值 | 中文 | 角度分配 |
|---|---|---|
| `sector` | 扇形（默认，等于现在的行为） | 从 −散角/2 到 +散角/2，**含两端** |
| `ring` | 环形 | 360° 等分，**不含端点**，首尾不重合 |

默认值必须是 `sector`，这样**现有 8 个技能一个都不受影响**（这是硬要求：新增参数不得改变旧内容的行为）。

### 4.2 这套参数能表达出哪些形态

| 想要的形态 | 怎么配 | 落在哪一档 |
|---|---|---|
| 一圈打出去（你说的环形） | 环形 + 5 发 | 第一档 |
| 双向交叉（前后各 2 发） | 环形 + 4 发 | 第一档 |
| 密集窄扇（喷子） | 扇形 + 散角 15° | 第一档 |
| 并排齐射（一排平行箭） | 需要「并排」模式（偏移而非角度） | 第一档的扩展，多一个取值 |
| 随机乱射 | 需要「随机」模式 | 第一档的扩展 |
| 螺旋（边转边发） | 需要「时序 + 角度递增」 | 第二档 |
| 真环绕（绕角色转） | 需要轨道运动 | 第二档 |
| 回旋镖（飞回） | 需要返程逻辑 | 第二档 |

**第一档先做「环形」和「扇形」两个取值**，其余留扩展口。不要一次做八个。

### 4.3 兼容性与黑名单

用现有机制就能表达，不需要新字段：

- **谁能装**：辅助石声明「需要投射物标签」，与现有写法一致。
- **谁不能装**：用「排除标签」。比如已经装了环形石的技能，由环形石自己追加一个标记标签，第二颗环形石看到这个标记就拒绝——**防止同一效果叠两次**。
- **引导技能不能装**：排除「引导」标签即可（这正是流放之路的做法）。

### 4.4 代价设计（这里有一个真缺口，必须告诉你）

形态类效果如果不带代价，会变成必带。流放之路的代价是「伤害折扣 + 蓝耗倍率」。我们的现状：

| 代价手段 | 现状 | 能不能用 |
|---|---|---|
| 蓝耗倍率 | 辅助石自带这个字段 | **能，现成** |
| 伤害折扣 | **没有「全局伤害」这个属性**。伤害是按元素分开算的（物理、火、冰、雷、混沌各算各的） | **不能直接用**，这是真缺口 |

两条路：

- **路 A（零架构改动）**：给这颗石头挂 5 条元素伤害减益（物理 −20%、火 −20%……）。缺点很脆：以后加新元素要记得补，且「减 20% 物理」和「减 20% 伤害」在语义上不等价（会被其他元素加成稀释）。
- **路 B（推荐）**：新增一个「全局伤害倍率」属性，在伤害管线末端乘一次。改动是「1 个属性 + 1 处乘法」，但这个属性的通用价值很高——以后所有「更多/更少伤害」的辅助石、装备词缀、状态都能用它，不必再按元素写五条。

**我推荐路 B**，理由是路 A 每加一种元素就要改一次内容，属于「今天的省事变成明天的债」。但这是架构扩展，需要你点头。

---

## 5. 会不会破坏上一批的 12 个技能定价

需要复核的组合（我的初判）：

| 技能 | 装环形石会怎样 | 判断 |
|---|---|---|
| 贯空箭 | 从「一条线穿 4 个」变成「一圈穿 4 个」 | 强度明显上升，必须靠伤害折扣与蓝耗压住 |
| 星屑连射 | 从「贴脸 5 发全中」变成「一圈 5 发」 | 反而是削弱（原本贴脸全中，现在摊开只中 1–2 发），可以少扣伤害 |
| 霜矛 | 变成「一圈 1 发」没有意义 | 应该禁止：单发技能装环形石无效果，需要一条「发数 ≥ 2 才能装」的前置判定 |
| 熔核引爆等范围技能 | 环形不适用 | 靠「需要投射物标签」自动挡掉 |

**这条很重要**：**单发技能装环形石等于白装**。必须在辅助石上写「发数至少 2 发」，否则玩家会装上去发现没反应，认为是程序错误。

## 6. 三个风险

1. **必带风险**：环形是「一眼看得见的强」，如果没有代价，所有投射物技能都会装。这也是为什么第 4.4 节的代价不能省。
2. **性能风险**：现在 5 发 × 80 敌的弹幕已经在压测基线附近（每秒 100 发、同屏 80 个角色）。环形 + 多重投射叠起来会让同屏弹数翻倍，需要重跑压测。
3. **设定一致性风险**：你的设定是「武器绑定初始技能，辅助宝石影响初始技能与稀有技能」。如果辅助石能大幅改形态，那「稀有技能」的独特性会被稀释——玩家可以用辅助石把普通技能改成稀有技能的样子。这条要你判断是否接受。

# 【存档原文】原始设计案/设计方案_技能基石三维模型_v1.md

# 技能基石的三维模型（对「行为 + 空间形状池」的核对与修正）

> **性质**：设计核对稿，没有改任何代码。针对你提出的「行为 + 空间形状是绑定的，两者组池就能有丰富多样的技能基石」这一判断。
> **结论先说**：**你的判断在代码里成立，而且比我的上一版方案更本质。** 但有三处需要修正，其中一处会直接决定成本。

---

## 1. 先给证据：形状确实是「焊死」在行为里的

我把四个判定点全找出来了，它们分别写在四个不同的地方，各写了一遍：

| 行为 | 判定形状 | 代码写法 | 位置（函数名） |
|---|---|---|---|
| 近战挥砍 | 扇形 | 比较「朝目标的角度」与「朝向」的差，超过半个扇角就跳过 | 沙盒 `_exec_melee` |
| 范围爆发 | 圆形 | 比较「目标到中心点的距离」与半径 | 沙盒 `_tick_aoe` |
| 引导 | 线形 | 算「点到线段」的距离 | 沙盒 `_tick_channel` |
| 投射物 | 点 | 每帧做圆形碰撞 | `projectile_field.gd` 的 `_strike_if_hit` |

**四种形状，四套实现，没有一处共用。** 这就是你说的「绑定」——不是设计上绑的，是**因为没人把它抽出来，所以它只能跟着行为走**。

而且系统层里根本没有「形状」这个东西：`systems/skills/` 下没有任何命中形状模块，判定全部写在沙盒的消费端。行为组件只产出「计划参数」，不负责判形状。

一个顺带的发现：**近战挥砍其实已经能做全周旋风斩**——把扇角配成 360°，角度差判定恒成立。只是没人这么配，也没人告诉你它可以。

---

## 2. 修正一：不是「行为 × 形状」两个维度，是三个

你说的「行为」里其实混了两件不同的事：

- **投送方式**：技能怎么到达目标（飞行的弹、瞬时的挥砍、持续的引导、位移的冲、贴自身的增益、召出来的随从）
- **结算时序**：几次、间隔多久、延迟多久（单段 / 多段 / 延迟 / 持续）

把「形状」单独拎出来，就是三维：

| 维度 | 取值 | 谁决定 |
|---|---|---|
| 投送方式 | 飞行 / 瞬时 / 引导 / 位移 / 自身 / 召唤 | **代码**（运行时行为不同，必须写） |
| 判定形状 | 点 / 线 / 扇 / 圆 / 环 / 自身 | **可以纯配数据** |
| 结算时序 | 单段 / 多段 / 延迟 / 持续 | **可以纯配数据** |

**这是最重要的修正**：你说的「行为 + 形状池」里，**形状能池化，行为不能**。飞行和引导是两种完全不同的运行时逻辑（一个每帧推进、一个按周期触发），不可能靠配置互相转换。所以池化只对「形状」和「时序」有效，对「投送方式」无效。

---

## 3. 修正二：不是笛卡尔积，是一张稀疏表

现有 7 个行为，其实就是这张三维表里的 **7 个格子**：

| 行为 | 投送 | 形状 | 时序 |
|---|---|---|---|
| 投射物 | 飞行 | 点（方向由散角摊开） | 命中即结算 |
| 近战挥砍 | 瞬时 | 扇（可到 360° = 全周） | 单段 |
| 范围爆发 | 瞬时（可延迟） | 圆 | 可多段 |
| 引导 | 引导 | 线 | 周期触发 |
| 冲刺 | 位移 | 线（路径） | 单段 |
| 自身增益 | 自身 | 自身 | 持续 |
| 召唤 | 自身 | 随从 | 持续 |

**表里空着的格子，就是你说的「技能基石池」。** 举几个明确有玩法价值的空位：

| 空位 | 组合 | 玩家看到的东西 | 价值 |
|---|---|---|---|
| 1 | 飞行 × 圆 | 飞出去再炸的弹（火球） | 现有范围爆发只能原地放，缺"投掷"手感 |
| 2 | 瞬时 × 线 | 一道光束 / 穿透射线 | 现有线形只有引导那条，缺瞬发版 |
| 3 | 瞬时 × 环 | 冲击波（中间空心，只有外圈命中） | 与圆形完全不同：贴脸反而安全 |
| 4 | 瞬时 × 扇 × 多段 | 三段连斩 | 现有近战只有单段 |
| 5 | 引导 × 圆 | 原地旋转扫射 / 持续灼烧圈 | 现有引导只有直线 |
| 6 | 引导 × 扇 | 扇形喷火 | 同上 |
| 7 | 瞬时 × 圆 × 延迟 × 多段（不同延迟） | 多点依次爆炸 | 现有只能同点同段 |
| 8 | 召唤 × 环 | 环形召出 4 个随从 | 现有召唤固定单点 |

**但有些格子是废的，必须排除**：自身增益 × 环形、冲刺 × 圆、召唤 × 扇——这些组合没有语义。所以是**稀疏表**，不是全集。这正是你说的「池」需要配「白名单」的原因：每个投送方式只允许一组形状。

---

## 4. 修正三：「丰富多样」不等于「格子多」

这里有个反直觉的点，我用现有数值说明：

现在 7 个行为 + 8 个技能，已经能打出**每秒 200 的霜矛**和**3 连的雷光斩**，玩法上并不显得贫乏。真正让技能显得不一样的，是**形状带来的决策差异**，不是格子数量。

一个具体例子：上表第 3 格的「环形冲击波」——中间空心，只有外圈命中。它和我已经规划的「裂地余震」（实心圆）在数值上可以完全一样，但**玩家的站位决策完全相反**：实心圆要往外跑，空心环要往里钻。**同样的数字，两种玩法。**

所以我的建议是：**不要追求填满表，要追求"每一格对应一个不同的决策"**。8–12 个有效格子足够撑起一个技能池，40 个格子大概率会有一半是"数字不同、决策相同"的废格。

---

## 5. 三条路线，成本差很多

### 路线一：不解耦，需要什么就加什么行为

- 做法：每要一个新格子，写一个新行为组件（约 100–200 行，含判定与回收）
- 优点：不动现有架构，风险最低，黄金用例不受影响
- 缺点：判定逻辑会重复 5–8 遍；每加一个都要重写"怎么判命中"
- 适合：只打算补 3–5 个格子

### 路线二（推荐）：先把「形状」抽成一个纯函数模块

- 做法：把散落的四段判定收拢成一个无状态的形状模块，输入（原点、朝向、形状类型、参数），输出「这个点是否命中」。四个消费点改成调用它。
- **关键优点**：不改行为结构、不改计划格式、不改任何现有数值——**257 个用例的基线不动**。只是把「四段重复代码」换成「一个模块 + 四次调用」。
- 立刻获得：范围爆发能配线形/环形，引导能配扇形/圆形，近战已经能配全周。
- 成本：约一天（含单测）
- 适合：打算补 5–15 个格子，也就是你说的「基石池」

### 路线三：完整三维引擎（投送 / 形状 / 时序 全部解耦）

- 做法：形状模块 + 时序调度器 + 投送器三层分离，行为退化为配置
- 优点：表达力最大化，理论上"配表造技能"
- 缺点：这是架构级重构，动的是命中闭环；所有黄金用例要重跑重校；沙盒里的判定要搬进系统层
- 成本：3–5 天，且期间不能并行做内容
- **我的判断：目前不值得。** 你的技能数量目标还没到需要它的量级（见第 7 节问题 3）

---

## 6. 「形状池」落地后的样子

形状抽出来之后，内容侧只需要在技能里写两个字段：

| 字段（中文） | 取值 |
|---|---|
| 判定形状 | 点 / 线 / 扇 / 圆 / 环 |
| 形状参数 | 半径、扇角、线长、环宽、环内径 |

而「投送方式」仍然是行为（还是那 6 个），「时序」还是那几个参数（段数、段间隔、延迟）。

于是造一个新技能的流程变成：

> 选投送（飞行/瞬时/引导）→ 选形状（点/线/扇/圆/环）→ 填参数（半径/角度/段数/延迟）→ 写一个内容文件

**不需要写代码的只有后两步。** 第一步换投送方式仍然要写代码，这一点必须说清楚，免得以后发现"说好的配表造技能呢"。

---

## 7. 三个问题（这些需要你判断，我给不了答案）

**问题一：你说的「技能基石」，是给玩家看的分类，还是给程序用的结构？**

- 如果只是**图鉴/UI 上的分类**（让玩家理解"这是扇形技能、那是环形技能"），那**根本不需要解耦**，内容层加个标签就够，零代码。
- 如果是**程序结构**（策划配表就能造出新技能），才需要第 5 节的路线二。

这两个需求成本差十倍。我猜你要的是后者，但请确认。

**问题二：你希望「不写代码」到什么程度？**

- A：允许每个新"投送方式"写代码，但形状和时序纯配 → 路线二就够
- B：连投送方式也想配出来 → 需要路线三，且实际上做不到（飞行和引导的运行时逻辑无法数据化）

**问题三：技能数量目标是多少个？**

- 40 个以内：路线一（需要什么加什么）更划算，重构的钱不如用来做内容
- 40–150 个：路线二（形状池）是最优解
- 150 个以上：才轮到路线三

这个数字决定一切。你之前提过 99 关主线 + 12 角色，按每角色 8–12 个技能估算大概是 100–150 个——如果是这个量级，**路线二是正确的投入**。

## 8. 我的建议（一句话）

**做路线二：先把形状抽成一个纯函数模块，再把「形状」开放给内容配置。行为继续用代码写（6 种够用），时序继续用参数配。这样你能拿到你说的「行为 + 形状池」里 80% 的表达力，成本是一天，且不动任何现有基线。**

剩下的 20%（飞行 × 圆、引导 × 圆这类）需要新投送逻辑，按需一个个加，不要一次铺开。

# 设计方案：技能基石「池抽取」三层渐进玩法 v1

> 状态：纯设计稿，未落盘任何代码/内容。等待制作人复审。
> 写作依据：本轮实测查证了三个业界先例（见文末附录），所有结论都有出处，不是拍脑袋。

---

## 1. 制作人原始构想（复述确认）

1. 制作人（人 + AI）产出 **N 个技能基石**（行为 + 形状 + 关键参数）。
2. 每个基石挂着对应的「**池**」，玩家随机抽取池里的内容：
   伤害、冷却 / 充能、每秒伤害倾向、触发其他效果的判定……
3. 整套拼成新技能后，**自动生成标签**。
4. 后续辅助宝石继续修改这套技能的参数。
5. **三期推进**：
   - 初期：制作人出 N 个**完整固定技能**（玩家学辅助宝石 × 遗物 × 技能的互动，参考 PoE2）；
   - 中期：玩家通过**固定基石**随机抽取对应池；
   - 中后期：玩家可以**随机抽取所有基石**。

## 2. 总判断：有游玩价值，且被业界验证过

| 先例 | 验证了方案的哪一段 | 证据要点 |
|---|---|---|
| **杀戮尖塔**（Slay the Spire） | 中期「固定骨架 + 随机池抽取」 | 制作者 GDC 2019 明说：奖励三选一是全游戏的核心决策点；每张牌都该「在有些卡组里对、有些卡组里错」。**受控随机 + 玩家选择**是这个模式成立的前提 |
| **Noita**（魔女之泉弹幕法杖） | 中后期「全随机构筑」 | 300 法术 × 100 天赋 × 8 法杖属性的组合爆炸，把「背构筑」变成「**用抽到的东西现场搭构筑**」——这是全随机段的乐趣来源。但它同时证明了代价：硬核到多数玩家过不了前期、零引导、靠社区维基补课 |
| **Path of Achra**（流放之路前传类） | 整体节奏：**开荒即成立** | 自称「残破构筑沙盒」，50+ 能力 × 种族 × 职业 × 神祇 = 1000+ 组合；关键在**第一局就能看到连锁反应成型**（闪电弹射→杀敌→尸体变僵尸→僵尸继续打），玩家才愿意反复开局 |

结论：三段式（固定 → 半随机 → 全随机）不是拍脑袋发明，是**把三个验证过的模式按学习曲线排列**。成立。

## 3. 三处必须修正（不修正会翻车）

### 修正一：「随机抽取」必须是抽三选一，不是系统直接发

- 杀戮尖塔的铁律：**「永远会选的选项不是决策，是条件反射」**。系统直接发随机结果 = 玩家零决策 = 没乐趣。
- 正确形态：抽到的东西以 **3 选 1 + 可跳过** 呈现（跳过本身要有价值，比如给少量资源）。
- 配套：稀有度权重 + **保底计数**（尖塔的做法：连出 N 张普通牌后稀有率递增，出稀有即重置）。

### 修正二：随机化必须「开局即见效」，不能是渐进拼图

- Path of Achra 的教训：构筑游戏最怕「乐趣在后头」。它刻意让玩家**第一局第一关就看到连锁成型**。
- 对本项目的含义：中期抽池时，每个基石的池里必须保证**每个抽项都至少能独立改变一次按键的手感**（比如抽到「触发判定」项，第一次触发就要能看见特效）。禁止「凑齐 5 件才开始好玩」。

### 修正三：中后期全随机基石，不能是均匀随机，要配「原型锚点」

- 全均匀随机的问题：会稀释流派身份（Noita 的代价就是死亡惩罚极重也依然方差巨大，玩家被迫靠维基）。
- 修正：基石抽取**按章节主题加权**（如火焰章：火系基石 60% 权重），且允许玩家**锁定 1 个已抽基石**（花局内资源）——「随机」里保留一颗自己选的钉子，构筑身份就还在。

## 4. 与本项目的对接（好消息：架构天然支持）

| 方案要素 | 现有系统 | 缺口 |
|---|---|---|
| 技能基石（行为+形状+参数） | 行为 7 种 + 形状判定已在规划抽形状模块（三维模型方案） | 形状模块尚未动工 |
| 池抽取（三选一） | 无 | 需新增「抽取表」数据结构 + 抽取界面（纯内容层） |
| 自动生成标签 | `tag_registry` 三类标签已有；内容对象都显式带标签 | 需定义**派生规则**（见 §5） |
| 触发其他效果判定 | 条件门（7 种判定 + AND + fail-closed）+ 触发器（链深 3）已建成 | 无，直接当池内抽项 |
| 辅助宝石改参数 | 辅助石系统 + 装配缓存已建成 | 无 |
| 组合爆炸的护栏 | §6.1 兼容黑名单机制（G7 拒绝装错）已有 | 池抽取结果要过同一套兼容判定 |

关键点：**中后期全随机不需要新架构**。基石 = 行为 + 形状 + 参数，这三样全是配置；随机只是在配置生成时用抽取表替代手填。护栏（黑名单、条件门 fail-closed、装配缓存）全部复用。

## 5. 「自动生成标签」的派生规则（必须先定，否则标签会变成噪声）

标签不能让程序自由发挥，必须是**确定性派生**：

1. 伤害类型标签 ← 从伤害包元素自动带出（已有）；
2. 行为标签 ← 基石行为决定（攻击/法术/移动……）；
3. 形状标签 ← 形状模块决定（近战/投射/范围/引导……）；
4. 特性标签 ← 只允许来自**白名单池抽项**（触发器、条件门各占一类），禁止从数值推标签；
5. 生成后**人工抽查率 20%**（前三个月），标签错 = 池表错，两头一起修。

这样标签既自动化又可控，玩家能用标签预判组合兼容性（PoE2 的核心读法习惯）。

## 6. 三期路线（对应制作人的初/中/中后期）

| 阶段 | 玩家做什么 | 制作人做什么 | 参照物 |
|---|---|---|---|
| 初期 | 用完整固定技能学辅助宝石 × 遗物 × 技能互动 | 手写 N 个完整技能 + 3 条教学关 | PoE2 技能+辅助教学 |
| 中期 | 固定基石 + 基石对应池三选一抽取 | 每个基石写池表（每池 ≥8 项，含 1 稀有）+ 保底规则 | 杀戮尖塔奖励屏 |
| 中后期 | 章节主题加权随机抽基石 + 锁定 1 个 | 章节权重表 + 原型锚点校验 | Noita（收敛版） |

**建议的首发规模**（科学起步，不铺满）：
初期 8 个完整技能（已规划 12 个里选 8）、中期 4 个基石 × 各 8 项池、中后期先只对 2 个章节开加权随机。跑通再加。

## 7. 风险清单（都要有对策才立项）

| 风险 | 严重度 | 对策 |
|---|---|---|
| 组合爆炸导致数值失衡 | 高 | 池项带「强度预算」字段，抽取时按预算配平（参考修正一里的伤害折扣先例） |
| 玩家看不懂随机技能 | 高 | 技能详情页强制显示派生标签 + 一次完整伤害公式预览；Noita 的教训就是没这个 |
| 随机出「死技能」（无手感差异） | 中 | 每个池项入库前过「决策差异」检查（三维模型方案的「一格一决策」原则） |

| 中后期随机稀释流派 | 中 | 章节加权 + 锁定机制（修正三） |
| 抽取界面开发量被低估 | 低 | 初期可先在实验台（沙盒实验场景）验证抽取逻辑，UI 后做 |

## 8. 比原案更有趣的两个增量（可选，按优先级排）

1. **「重抽」资源**：局内获得一种消耗品，可对任意抽项重抽一次。给随机失败一个主动补救出口，把挫败转化为决策（尖塔「跳过也是选择」的同源逻辑）。
2. **「组合发现图鉴」**：第一次跑出某个（基石 × 池项 × 辅助）组合时记入图鉴并给小额永久奖励。Noita 社区「死亡驱动学习」的正向版：鼓励玩家主动探索组合，而不是被动维基补课。

2. 中后期「章节加权 + 锁定 1 个」的收敛设计，认可吗？（完全不收敛 = Noita 式高方差，也可接受，但要配套更硬的死亡惩罚哲学）

**数量冻结为 v1**：加任何新轴值都算口径变更，需修订本表。

### 二、主动技能漏项的总称（问题 2 的回答）

八项字段统称「**施放参数**」，所在的这一层统称「**施放层**」。分三小组：

| 小组 | 字段 | 说明 |
|---|---|---|
| 成本参数 | 耗蓝、消耗类型、冷却、充能数、充能回复 | 回答「这次施放付什么、多久能再放」 |
| 节奏参数 | 前摇、等级曲线 | 回答「多快出手、怎么成长」 |
| 装配参数 | 部件绑定、允许辅助标签 | 回答「基石怎么挂、辅助怎么配」 |

每秒伤害不在其中——它是设计表的导出列（问题 1 已裁定）。

### 三、「一切皆标签」的定稿口径（问题 3 + 制作人裁定）

制作人裁定：**每个轴值自带一个标签，辅助宝石按标签区分**。这与引擎现状同构（已核对），
定稿口径如下：

1. **标签来源分三类**：
   - **初生标签**：四轴各派生 1 个（投送、形状、时序、流派）+ 元素标签（来自伤害包：物理/火/冰/雷/混沌）。**元素不是轴**——否则格子数要乘 5，此条写死；
   - **收敛标签**：辅助宝石的 `add_tags` 给技能追加的标签（引擎已实现，多轮收敛）；
   - **特性标签**：池抽项 / 触发器 / 条件门专属，白名单制。
2. **技能标签 = 初生标签 ∪ 收敛标签 ∪ 特性标签**。
3. **辅助宝石的双向声明**（引擎已有，口径命名统一）：
   - `require_tags` 需要标签：全部具备才兼容；
   - `exclude_tags` 禁止标签：命中任一即拒绝；
   - 判定顺序：**先查禁止，再查需要**。
4. **「屏蔽」只有一种机制**：禁止标签。三个挂点（技能级 `allowed_support_tags`、辅助宝石级 `exclude_tags`、独占组 `conflicts_with`）都是它的变体，不发明第二种屏蔽方式。制作人说的「扩展时屏蔽轴内参数的标签或池」就落在技能级挂点上。

### 四、多部件技能的标签规则（v1.1 新发现的漏洞及裁定）

**漏洞**：双部件技能（冲刺+增益）两套轴会产生两套初生标签，若在技能级合并，会出现「冲刺标签 + 增益标签同时存在」的污染——某颗「近战专属辅助」可能意外装到冲刺部件上。

**裁定（已定稿，2026-10-21 制作人确认）**：
- 标签**按部件派生**，兼容判定在**部件级**执行——合并后判定，效果找不到归属；按部件判定，效果天然有归属；
- 技能级标签只做展示聚合（图鉴 / 详情页），不参与判定；
- 落地顺序：先按技能级做（现状即如此），部件级留接口，第一批双部件辅助上线前切换。

### 五、本节与原 §0 的关系

原 §0 的五个问题全部保留作记录；本节是制作人裁定后的**唯一现行口径**。冲突处以本节为准。

## 0. 制作人两条定义的审查结论（有问题，必须先看）

### 问题 1：「每秒伤害」不是粒子，是导出量

每秒伤害 = 有效伤害 × 段数 ÷（前摇 + 冷却），它由**其他粒子算出来**，不能反过来当输入字段。
而且生存类（磐石架势）、召唤类（长明烛火）技能**没有**每秒伤害这个概念。
**裁定**：从粒子清单移除，在设计表中降级为「导出列」（给人看平衡用的）。

### 问题 2：主动技能 = 基石 + 五项数值，**漏了 4 个引擎已有的字段**

引擎 `SkillData` 的完整字段（已核对）：

| 字段 | 中文含义 | 你的清单 | 结论 |
|---|---|---|---|
| 伤害 / 耗蓝 / 冷却 / 前摇 | — | ✅ 有 | — |
| `cost_type` | 消耗类型（蓝/生命/无） | ❌ 漏 | 必补，否则「生命消耗换强度」做不了 |
| `max_charges` + `charge_recharge_time` | 充能数 + 充能回复 | ❌ 漏 | 必补，引擎已实现，是「冷却」的替代粒子 |
| `level_scaling` | 等级曲线 | ❌ 漏 | 必补，决定成长手感 |
| `parts` | 部件绑定（基石挂载点） | ❌ 漏 | 必补，多部件技能（冲刺+增益）靠它 |
| `allowed_support_tags` | 允许的辅助标签 | ❌ 漏 | 必补，兼容黑名单的数据入口 |

**裁定**：主动技能 = 基石 + **伤害、耗蓝、冷却、前摇、消耗类型、充能、等级曲线、部件绑定** 八项。

### 问题 3：漏了第 4 轴——「流派归属」（攻击 / 法术）

现有内容里「攻击」「法术」两种归属**与投送方式无关**（攻击·投射物、法术·增益都存在），
而辅助宝石的兼容性靠它区分（近战辅助装不到法术上）。
**裁定**：粒子模型必须是**四轴**：投送方式 × 判定形状 × 结算时序 × 流派归属。
第 4 轴只有 2 个值、零参数，成本极低但不加它标签就派生不出来。

### 问题 4：「所有变化」不能是全乘积，必须稀疏化

四轴全乘积 = 6 × 7 × 4 × 2 = **336 格**，其中大量是废格（自身×环形、召唤×扇形……）。
**裁定**：枚举分两层——轴全枚举（穷尽可能性，写文档零成本）+ 有效格白名单（真做成行为的格子）。
下面 §3 的矩阵就是白名单本体：336 格中**有效 130 格 / 边缘 56 格 / 废格 150 格**（含第 4 轴翻倍）。

### 问题 5（方法论，帮你省一半配置量）：关键参数挂在「轴」上，不挂在「基石」上

每个基石的关键参数 = 它三条轴的参数并集。这样参数表只需维护 **4 张轴表**（§4），
不用给每个基石单独写参数清单。这是数据驱动的正确粒度。

## 1. 粒子总定义（修正版）

```
行为名称 = 投送方式 × 判定形状 × 结算时序 × 流派归属
基石     = 行为名称 + 关键参数（= 三条轴的参数并集）
主动技能 = 基石 + 伤害 + 耗蓝 + 冷却 + 前摇 + 消耗类型 + 充能 + 等级曲线 + 部件绑定
标签     = 四轴的确定性派生（§5），不从数值推
```

核心乐趣 = 「**一格一决策**」。枚举是分类学（文档成本≈0），实装是选择学（每格有成本）。分三级推进：

| 级 | 范围 | 何时做 |
|---|---|---|
| P0 | 现役 12 格（✅） | 已完成 |

| P3 | `RECT` 矩形、全部 △ 格 | 冻结，除非具体内容真需要 |

**三条精简铁律**：
1. 轴值冻结：6×7×4×2 就是 v1 粒子集，加新轴值要走变更（防蔓延）。
2. 每格实装前过「决策差异」验收：和已有任何一格站位于法相同就不做。
3. 废格永久封禁并写明理由（结构性无意义），防止后人「补全」出垃圾行为。
