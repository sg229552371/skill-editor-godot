> **这份是本模块最重要的产出。** 代码只是载体，结论才是资产。
> 实验目的：检验技能系统的五条治理判据能否搬到**另一种类型的系统**（背包）上。
>
> 时间：2026-10-22 ｜ 级别 S1 ｜ 状态：**已跑完，结论已出**

## 一、实验设计

### 1.1 为什么选背包系统

技能系统是**声明式数据 → 运行时组装**；背包系统是**空间约束 + 状态变更**。
两者在"数据如何生效"上机制完全不同，正好能检验判据是"通用"还是"贴着技能系统长的"。

如果换成第二个也在做"数据→组装"的系统（比如装备、天赋树），判据几乎必然成立——
那是一次没有信息量的实验。

### 1.2 检验方式：反向注入

**一个从未红过的门禁，不算门禁。** 五条判据里能落成门禁的（P1/P2/P3），
都做了一次人工注入"故意犯错"，确认门禁真的变红，再恢复。

| 判据 | 门禁落点 | 注入的错 | 结果 | 具体报错 |
|---|---|---|---|---|
| P2 声明面 | `test_every_item_declares_valid_geometry` | 把 `herb.tres` 的 `grid_w` 改成 0 | ✅ **红了**（8 用例失败） | `herb → grid_w/grid_h 必须 ≥1（当前 0×1）` |
| P1 单真源 | `test_container_cells_equal_declared_geometry` | 容器 `_occupy()` 硬编码 1×1，偏离声明 | ✅ **红了**（7 用例失败） | `scroll_blink 占用格数与声明不符（声明 3×2）` |
| P3 免费接口 | `test_no_item_id_hardcoded_in_systems` | `put()` 里加 `if item_id == "charm_ruby"` | ✅ **红了**（3 用例失败） | `inventory_grid.gd:84 if String(item.item_id) == "charm_ruby"` |

三次注入全部被拦，恢复后 30/30 全绿。**门禁是活的，不是装饰。**

## 二、五条判据的复刻结论

| 判据 | 技能系统里的形态 | 背包系统里成立吗 | 结论 |
|---|---|---|---|
| P1 单真源 | 轴值→`behavior_id` 映射只在白名单矩阵展开一次 | 物品占格尺寸只在 `.tres` 声明一次，容器读而不存 | ✅ **成立，但需要重新定义"什么是那份唯一事实"** |
| P2 声明面 | 辅助宝石自己声明 tags / 修正，机器核对 | 物品自己声明 `grid_w/grid_h/max_stack`，`validate()` 自检 | ✅ **成立，且比技能系统更自然** |

| P5 改动回写 | 台账 D-* + 图谱挂载 + 真源清单登记 | 本次**未实现**（见 §四） | ⚠️ **未验证** |

## 三、三条真发现（判据在背包上"变形"了）

这三条是实验的真正收获：判据成立，**但成立的方式和技能系统不一样**。
直接照搬技能系统的做法会做错。

### 3.1 P1「单真源」的对象会变，方法不通用

技能系统的唯一事实是**一张映射表**（轴值 → behavior_id），它是静态的、可穷举的。
背包系统的唯一事实是**物品尺寸**，但它同时出现在三处：

1. `.tres` 的 `grid_w/grid_h`（数据真源）
2. 容器里 `_cells` 的坐标集合（运行态缓存）
3. **还没写的 UI 图标尺寸**（表现层）

②③ 都不是"另一份真源"，而是**同一份事实的不同表达**。所以 P1 在背包上的正确形式不是
"只有一处写它"，而是"**其他处只能从真源派生，不允许独立修改**"。

> **教训**：P1 不能照抄成"搜索这个常量只允许出现在一个文件里"。
> 对派生量，正确断言是**一致性**（`容器占格 == 声明格`），不是**唯一性**。
> 技能系统那边也一样——只是它的派生量恰好少到可以"唯一"。

### 3.2 P2「声明面」在背包上比技能系统更适合

技能系统里，辅助宝石声明 tags 后，还要经过装配管线（六步 + 多轮收敛）才生效，
"声明"和"生效"之间隔着一段逻辑，所以要靠装配测试间接验证。

背包系统里，物品声明 `grid_w=2, grid_h=3`，容器**直接就按这个占格**，没有中间层。
于是 `validate()` → 门禁 → 占格核对 形成一条直链，声明错了立刻红。

> **教训**：**数据到行为的链路越短，声明面判据越强。**
> 反过来说，技能系统的声明面判据偏弱不是判据本身的问题，是它有装配层——
> 那正说明装配层需要独立的门禁（技能系统确实有，`test_m3_assembly_cache`）。

### 3.3 P3「免费接口」的真正敌人不是"要改代码"，是"要改测试"

实验中发现一个细节：写 P3 测试时，最自然的写法是

```gdscript
assert_eq(g.count_of(&"herb"), 5)   # ← 列举了具体物品
```

这样写，**新增物品时这条测试要跟着改**，免费接口就名存实亡了——
不改 `.gd` 但改 `.tes`… 改测试，等于换了个地方付成本。

所以 P3 测试必须**动态遍历目录**，不含任何具体 item_id：

```gdscript
for item in _all_items():        # 扫 content/items/*.tres
    ...                          # 断言只依赖 ItemData 的字段
```

> **教训**：**判据的测试本身必须遵守判据。**
> 一条"新增内容不用改代码"的判据，如果它的验证代码要改，那它没被验证。
> 这一条对技能系统同样适用——已有测试里有大量 `&"fireball"` 这样的硬编码，
> 它们让"新增技能不改代码"这条判据在测试层面并不成立。

## 四、P5「改动回写」未能验证，原因值得记下来

技能系统的 P5 由三件东西承载：台账（`D-*` 决策）、记忆图谱（每个 `D-*` 必须挂载）、
真源清单（每份文档必须登记）。三者都有门禁。

背包系统**做不到**，原因很实在：

| 缺什么 | 为什么技能系统有而背包没有 |
|---|---|
| 台账 | 台账记录的是"做了个非显然的决策"。背包目前只有 6 个物品、2 个 `.gd`，**没有值得记的决策**。硬造台账 = 造文档垃圾 |
| 图谱 | 图谱是为"AI 接手要追溯依据"服务的。技能系统有 10 个节点因为它经历过 3 次路线摇摆；背包没有摇摆，没有可追溯的分叉 |
| 真源清单 | 清单管的是"哪份文档是现行口径、哪些是过程稿"。背包只有 2 份文档，且都是现行口径，不存在"读错版本"的风险 |

> **结论：P5 不是"通用判据"，它是"复杂度过阈值后的必需品"。**
>
> 判据的适用条件应该写成：**当一个系统出现"多个版本的说法"或"非显然的决策"时，P5 才启用。**
> 在复杂度不足时强上 P5，就是本项目此前那个问题——治理成本超过产出成本。

这是本次实验**最反直觉的一条**：五条判据里唯一没能复刻的那条，
不是因为它不通用，而是因为**新系统还没复杂到需要它**。

## 五、对技能系统的三条回馈

实验不是单向的。背包系统反过来暴露了技能系统的问题：

| # | 技能系统的问题 | 背包系统怎么照出来的 | 建议 |
|---|---|---|---|
| R-1 | **测试里大量硬编码具体内容 id**（`&"fireball"` 等），使"新增内容不改代码"在测试层不成立 | 背包的 P3 测试强制动态遍历目录，才发现"硬编码 id 的测试"本身就是免费接口的敌人 | 技能系统的内容测试应改为"遍历 `content/gems/**` + 只断言结构性事实"，具体数值走单独一份数据快照 |
| R-2 | **P1 的表述过于绝对**（"只能一处定义"） | 背包的尺寸必然出现三处（数据/运行态/UI），逼出"派生 vs 真源"的区分 | 把 P1 改述为：「真源只有一处；派生量必须有一致性门禁」 |
| R-3 | **治理成本已超过产出成本** | 背包 2 个 `.gd` + 6 个物品 → 2 份文档；技能系统 3894 行代码 → 9894 行文档 | P5 应设**启用条件**而非默认启用（见 §四） |

## 六、最终裁定（供制作人确认）

| 项 | 裁定 |
|---|---|
| 五条判据能复刻到背包系统吗 | **能，4/5 成立**（P5 条件未满足，非不成立） |
| 判据要不要做成通用 skill 插件 | **不建议**。可复用的是**判据**，不是步骤。步骤（台账/图谱/清单三层）是技能系统复杂度的产物 |
| 背包模块要继续做成正式系统吗 | **建议停在这里**。实验目的已达成，继续做会重演"治理超过产出" |
| 技能系统该改什么 | 按 §五 R-1 改内容测试（**优先级最高**，这是真的漏洞） |
